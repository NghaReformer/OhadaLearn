## 1. Bugs & Issues

### MEDIUM — Hardcoded hex inside SVG data URI (accent color decoupled from token)

**File:** `src/lib/components/playground/PlaygroundSettings.svelte:94`  
**Rule:** No hardcoded hex outside `src/lib/theme/tokens.ts`.  
The dropdown chevron is rendered as an inline SVG `background-image` data URI with `stroke='%237c7fff'` (`#7c7fff`). CSS custom properties (`var(--accent)`) cannot be interpolated inside `url()` data URIs, so this color is permanently hardcoded. If `--accent` changes in tokens, the chevron silently shows the wrong color.  
**Suggested fix:** Replace the data-URI approach with a CSS mask pattern:

```css
.setting-select::after {
  content: '';
  -webkit-mask: url('/icons/chevron-down.svg') no-repeat center;
  mask: url('/icons/chevron-down.svg') no-repeat center;
  background-color: var(--accent);
}
```

Or extract the SVG to `static/icons/chevron-down.svg` and reference it via `background-image: url('/icons/chevron-down.svg')` + `filter` tint.

### MEDIUM — In-memory rate limiter ineffective on serverless (Vercel)

**Files:** `src/routes/api/waitlist/+server.ts:6` · `src/routes/api/feedback/+server.ts:8`  
Each endpoint declares a module-level `rateLimitMap`. On Vercel, each invocation may spin up a new cold-start function; the map is reset every time, making the 5-per-minute cap illusory under concurrent traffic or cold-start conditions. The waitlist comment acknowledges this ("sufficient for Phase 1"), but the feedback endpoint has no such note.  
**Suggested fix:** For Phase 1, add a comment to the feedback endpoint matching the one in waitlist. For Phase 2, replace with Upstash Redis rate limiting (compatible with Vercel Edge Functions) or a Supabase counter column with a TTL.

### LOW — Hardcoded `#fff` bypasses token system

**Files:**
- `src/routes/[lang]/learn/+page.svelte:202` — `color: #fff;`
- `src/routes/[lang]/chart-of-accounts/+page.svelte:423` — `color: #fff;`
- `src/routes/[lang]/chart-of-accounts/+page.svelte:458` — `color: #fff;`

White text on dark/accent backgrounds is intentional, but it bypasses the token system. If the surface color changes (e.g., a theme variant), the text remains white with no easy audit trail.  
**Suggested fix:** Add `--text-on-accent: #fff;` to `src/lib/theme/tokens.ts` and replace all three occurrences with `color: var(--text-on-accent);`.

### LOW — Hardcoded hex fallbacks in CSS custom properties (bank reconciliation)

**File:** `src/lib/playgrounds/bank-reconciliation/components/ReconciliationFlow.svelte:137,144,207,208,270,275,278,281`  
Multiple occurrences of `var(--accent, #6ea8fe)`, `var(--green, #22c55e)`, `var(--orange, #f59e0b)` — hardcoded fallback values that will silently display wrong colors if the token isn't injected (e.g., in an iframe or test environment that doesn't load the layout).  
**Suggested fix:** Remove the hex fallbacks and instead ensure the CSS custom properties are always defined — they are injected by the layout's `css-generator.ts`, so the fallbacks are defensive-dead code. If a fallback is genuinely needed for standalone SVG use, define a scoped `:root {}` in the component.

### LOW — `console.warn` for duplicate playground slug registration is a runtime footgun

**File:** `src/lib/playgrounds/_registry.ts:14`  
A duplicate slug logs a warning and silently overwrites the first registration. In production, a mis-import could cause the wrong playground to render with no error thrown or visible state divergence.  
**Suggested fix:** In development builds, throw an `Error` on duplicate registration. In production, return early without overwriting and include the slug name in the warning message for faster diagnosis.

### Playground A — Financial Ratio Dashboard

**EN:** Financial Ratio Analysis · **FR:** Analyse des Ratios Financiers  
**Target learner:** Licence 3, Master 1, practicing accountant  
**Pedagogical objective:** Students can compute ratios individually but struggle to read them together as a coherent picture of firm health. This playground fixes the "silo" problem — ratios are meaningless in isolation; the tool forces interpretation of clusters.  
**Core interaction:** User inputs a simplified balance sheet and income statement (pre-populated with a realistic SYSCOHADA firm); the playground computes and visualises three ratio families (liquidity, solvency, profitability) on a radar chart. User can drag sliders to stress-test one input and watch which ratios tip into "danger" territory.  
**Minimum viable inputs:** Current assets, current liabilities, total assets, total debt, revenue, EBIT, net income  
**Minimum viable outputs:** Current ratio, quick ratio, debt-to-equity, interest coverage, ROA, ROE, ROCE; radar chart; colour-coded alert badges  
**Complements existing:** TVM and CVP playgrounds provide forward-looking analysis; this playground closes the loop with backward-looking performance measurement from historical financial statements.

---

### Playground B — VAT / TVA Return Builder

**EN:** VAT Return Calculator · **FR:** Déclaration de TVA  
**Target learner:** Licence 2, practicing accountant, tax preparer  
**Pedagogical objective:** TVA declarations are the most common compliance task in OHADA-zone firms. Students confuse input VAT (TVA déductible), output VAT (TVA collectée), and the net payable/creditable position, especially with partial exemption.  
**Core interaction:** Learner records a set of purchase and sale transactions (with or without VAT, at 19.25% CEMAC rate or configurable for UEMOA/WAEMU rates). The playground builds a live TVA summary table, shows the journal entries generated by each line, and computes the net balance due or credit carried forward.  
**Minimum viable inputs:** List of transactions (amount HT, VAT rate, purchase/sale flag), accounting period  
**Minimum viable outputs:** TVA collectée, TVA déductible, net TVA à payer / crédit reporté, summary table, auto-generated journal entries using SYSCOHADA accounts (4431, 4452, 4455)  
**Complements existing:** Journal Entry playground teaches the mechanics; this playground applies them to the most common real-world compliance workflow.

---

### Playground C — Payroll Calculator (Bulletin de Paie)

**EN:** Payroll Slip Builder · **FR:** Simulateur de Bulletin de Paie  
**Target learner:** Licence 3, Master, HR/payroll practitioner  
**Pedagogical objective:** OHADA-zone payroll involves employer and employee contributions specific to CEMAC/OHADA jurisdictions (CNPS, IRPP, CRTV levy in Cameroon, etc.). Students often apply generic formulas without understanding the tiered contribution structure.  
**Core interaction:** User inputs gross salary and selects the country/jurisdiction (Cameroon, Côte d'Ivoire, Sénégal — driving different rate tables). Playground generates a full bulletin de paie showing gross → net computation, employer cost, and the corresponding journal entries (accounts 641x, 431x, 447x).  
**Minimum viable inputs:** Gross monthly salary, employment category, dependents, jurisdiction  
**Minimum viable outputs:** Detailed pay-slip table (taxable base, each deduction line), net salary, employer total cost, journal entry, downloadable PDF layout  
**Complements existing:** Fills a practitioner gap not covered by any existing playground. Extends the Journal Entry playground by introducing payroll-specific chart-of-accounts usage.

---

### Playground D — Cash Budget (Budget de Trésorerie)

**EN:** Cash Budget Planner · **FR:** Budget de Trésorerie  
**Target learner:** Licence 2/3, small business owner  
**Pedagogical objective:** Students learn to prepare income statements but often can't distinguish profit from cash. This playground builds intuition for the profit-cash gap — a profitable firm can be insolvent.  
**Core interaction:** User builds a 6-month rolling cash budget by entering expected receipts (collections from customers with payment lag) and disbursements (supplier payments, payroll, taxes). Playground shows the monthly opening/closing balance, highlights months with negative cash position, and suggests the minimum credit line required.  
**Minimum viable inputs:** Starting cash balance, 6 months of revenue with collection delay (30/60/90 days), cost structure, tax payment months  
**Minimum viable outputs:** Month-by-month budget table (receipts, disbursements, net, balance), cash flow chart, "deficit alert" banner with required financing amount  
**Complements existing:** CVP playground models profitability; this shows why a profitable CVP outcome can still produce a cash crisis. Natural follow-on exercise in any managerial accounting course.

### Playground E — Depreciation Method Comparator (Native Svelte)

**EN:** Depreciation Method Comparator · **FR:** Comparaison des Méthodes d'Amortissement  
**Target learner:** Licence 2, Licence 3  
**Pedagogical objective:** The static `depreciation-playground.html` teaches each method in isolation. Students exit without understanding *why* the choice of method matters for tax vs. book reporting, or how the methods diverge over an asset's life.  
**Core interaction:** User enters an asset (cost, useful life, residual value). The playground renders all three SYSCOHADA-compliant methods side-by-side (constant/linear, declining-balance, sum-of-years-digits) with a comparative chart overlaying the three depreciation expense curves and three net book value curves. A "tax shield" callout shows the NPV of the tax deduction under each method.  
**Minimum viable inputs:** Cost, salvage value, useful life (years), applicable tax rate, discount rate  
**Minimum viable outputs:** Three-column schedule table (one column per method), dual-chart (depreciation expense + NBV), NPV of tax shield comparison, auto-generated journal entries  
**Complements existing:** Directly replaces the orphaned `static/playgrounds/depreciation-playground.html` with a native module that integrates with the preference store, i18n system, and share-URL mechanism already used by the other five playgrounds.
