**H1 — `$lib/server/db/types` imported in a client component**
`src/lib/components/feedback/FeedbackForm.svelte:7`
```ts
import type { FeedbackType, FeedbackSeverity } from '$lib/server/db/types';
```
SvelteKit enforces the `$lib/server/` boundary at the module-resolution level. Although TypeScript erases `import type` at transpile time, the boundary check can fire before stripping depending on the adapter/Vite version, and it is explicitly prohibited by CLAUDE.md ("Server-only code goes in `$lib/server/` — SvelteKit enforces the boundary"). The two types are plain string unions with no server-only dependencies.
**Fix:** Move `FeedbackType` and `FeedbackSeverity` to a new `src/lib/types/feedback.ts` (or to `src/lib/server/db/types.ts`'s export re-exported from a non-server path) and update imports in both the component and the server handler.

**M6 — `requestFullscreen()` result not awaited; `isFullscreen` can become stale**
`src/routes/[lang]/playgrounds/[slug]/+page.svelte:47–48`
```ts
target.requestFullscreen();  // Promise — not awaited
isFullscreen = true;         // set unconditionally
```
`requestFullscreen()` rejects if the browser refuses (e.g., no user gesture in some Safari versions, or the element is detached). The rejection is silently dropped, `isFullscreen` stays `true`, and the button label shows "Exit Fullscreen" for a fullscreen that never activated. The `fullscreenchange` event only fires on success, so the `$effect` listener does not self-correct.
**Fix:**
```ts
function toggleFullscreen() {
  const target = data.isNativeModule ? nativeContainerEl : iframeEl;
  if (!target) return;
  if (!document.fullscreenElement) {
    target.requestFullscreen().catch(() => {}); // isFullscreen updated by fullscreenchange
  } else {
    document.exitFullscreen().catch(() => {});
  }
  // Remove the manual isFullscreen = true/false — let fullscreenchange be the source of truth
}
```

### P1 — Bilan Comptable (SYSCOHADA Balance Sheet Builder)

**Title (EN/FR):** Balance Sheet Builder / Constructeur de bilan  
**Target learner:** Licence 2, Licence 3  
**Pedagogical objective:** Students can produce individual journal entries but consistently struggle to see how the trial balance maps to the SYSCOHADA condensed balance sheet (Bilan Actif / Passif). The playground closes the loop between the journal-entries playground and the final financial statement.  
**Core interaction:** The learner is given a pre-seeded trial balance with a mix of asset, liability, equity, income, and expense accounts (using SYSCOHADA class codes). They drag accounts into the correct balance sheet sections (Actif immobilisé / Actif circulant / Trésorerie-Actif / Capitaux propres / Dettes, etc.). A live running total reveals whether the balance sheet balances.  
**Minimum viable inputs / outputs:**
- Input: editable trial balance (account code, name, debit/credit amount)
- Output: formatted SYSCOHADA balance sheet with automatic netting, subtotals per class, and a balance-check indicator  
**Complements existing:** The Journal Entries playground generates individual entries. This playground is the natural downstream step — from entry → ledger → balance sheet — completing the accounting cycle narrative.

### P2 — Valorisation des Stocks / Inventory Valuation (PMP & FIFO)

**Title (EN/FR):** Inventory Valuation / Valorisation des stocks  
**Target learner:** Licence 2  
**Pedagogical objective:** PMP (Prix Moyen Pondéré / Weighted Average Cost) is mandatory under SYSCOHADA for goods accounts. Students frequently confuse PMP recalculation timing (perpetual vs. periodic) and conflate it with FIFO. The playground builds intuition for how stock flows change the carrying value.  
**Core interaction:** The learner inputs a sequence of purchase and sale transactions (quantity + unit price). The playground displays a real-time stock card (fiche de stock) in PMP or FIFO mode side-by-side, showing how unit cost and total stock value differ between methods. Clicking a row explains the calculation step.  
**Minimum viable inputs / outputs:**
- Input: transaction sequence (date, type = purchase/sale, qty, unit price), method selector
- Output: stock card (fiche de stock) with running unit cost, total stock value, and cost of goods sold per transaction  
**Complements existing:** Journal Entries covers the debit/credit mechanics. Inventory Valuation feeds the Classe 3 account amounts that become inputs to those journal entries — bridging the two playgrounds directly.

### P3 — Fiche de Paie / Payroll & Social Contributions

**Title (EN/FR):** Payroll Calculator / Calculateur de fiche de paie  
**Target learner:** Licence 3, practicing professional  
**Pedagogical objective:** Salary accounting is one of the most-tested practical skills for SYSCOHADA students, yet the interaction of gross salary, CNSS employee/employer shares, IRPP, and net-to-pay is routinely miscalculated. The playground makes the relationship between the pay slip (fiche de paie) and the payroll journal entry tactile.  
**Core interaction:** The learner enters gross salary and selects a country (Cameroon, Senegal, Ivory Coast — each with different CNSS ceilings and IRPP brackets). The playground computes CNSS employee/employer, IRPP, and net pay with a visual waterfall chart. A second pane shows the SYSCOHADA journal entry (compte 661, 4311, 4312, 4313, 4321, 5211) auto-generated from the calculation.  
**Minimum viable inputs / outputs:**
- Input: gross salary, country, category (salaried / cadre), period
- Output: pay slip summary, IRPP detail, CNSS breakdown, SYSCOHADA journal entry  
**Complements existing:** No existing playground covers statutory deductions. The journal entry output connects directly to the Journal Entries playground's learning content for wages (compte 66x).

### P4 — TVA / VAT Journal Entries & Declaration

**Title (EN/FR):** VAT Accounting / Comptabilité TVA  
**Target learner:** Licence 3, Master 1, practicing professional  
**Pedagogical objective:** Students regularly mis-classify TVA collectée vs TVA déductible and mistime the declaration. The key misconception is treating TVA as income/expense rather than a tax liability/asset wash-through.  
**Core interaction:** The learner enters a set of purchase and sale invoices with tax codes (rate 0 %, 10 %, 19.25 % for Cameroon). The playground builds the TVA ledger (compte 4455 / 4456 / 4457), computes the net TVA payable or credit, and generates both the accounting entries and the monthly declaration form. A toggle switches between the "real method" (TVA collected on billing) and the "cash method" (TVA on payment).  
**Minimum viable inputs / outputs:**
- Input: invoice table (type: purchase/sale, amount excl. tax, TVA rate), declaration period, TVA method
- Output: TVA ledger, net amount due/credit, journal entries, stylised declaration form  
**Complements existing:** No existing playground models indirect taxation. TVA feeds into the Bank Reconciliation playground (TVA payments appear in both the bank statement and the ledger) and the Balance Sheet Builder (TVA asset/liability positions on the balance sheet).

### P5 — Tableau de Financement / TAFIRE (Working Capital Flow)

**Title (EN/FR):** TAFIRE — Working Capital Flow / TAFIRE — Tableau de Financement  
**Target learner:** Master 1, Master 2, practicing professional  
**Pedagogical objective:** TAFIRE (Tableau Financier des Ressources et des Emplois) is the SYSCOHADA-specific working capital flow statement and is unique to the OHADA framework — no equivalent appears in IFRS or US-GAAP. Students at Licence level confuse it with a cash flow statement. The playground focuses on its two-part structure: variation du fonds de roulement net global (FRNG) and variation du besoin en fonds de roulement (BFR).  
**Core interaction:** The learner is given two consecutive SYSCOHADA balance sheets (N-1 and N). The playground auto-computes FRNG and BFR changes, then assigns each balance sheet movement to the correct TAFIRE section (Ressources / Emplois stables vs. variations du BFR). The learner can override line assignments and see whether the tableau balances. A visual cash-flow waterfall shows the net cash position change.  
**Minimum viable inputs / outputs:**
- Input: balance sheet line items for year N and year N-1, net income for year N
- Output: completed TAFIRE with automatic resource/employ classification, FRNG Δ, BFR Δ, and cash balance verification  
**Complements existing:** TAFIRE is the logical capstone of the Balance Sheet Builder (P1) — you need two balance sheets to build a TAFIRE. The trio (Journal Entries → Balance Sheet Builder → TAFIRE) forms a complete accounting cycle simulation unique to the OHADA curriculum.
