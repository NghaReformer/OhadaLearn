### BUG-01 · HIGH · Theme tokens `--orange`, `--blue`, `--red` never defined — hardcoded fallbacks always fire

**Files:** 27 occurrences across 7 components  
- `src/lib/components/playground/KpiStrip.svelte:76`
- `src/lib/playgrounds/amortization/components/ScheduleTable.svelte:240,246,259`
- `src/lib/playgrounds/amortization/components/InputsPanel.svelte:604–605`
- `src/lib/playgrounds/amortization/components/ChartPanel.svelte:436,444,493,501,515,529,533`
- `src/lib/playgrounds/bank-reconciliation/components/LedgerPanel.svelte:175`
- `src/lib/playgrounds/bank-reconciliation/components/VarianceScale.svelte:230,260,261,331,335,370`

**Explanation:** `css-generator.ts` emits `--amber`, `--green`, `--error` — but never `--orange`, `--blue`, or `--red`. Every `var(--orange, #f59e0b)`, `var(--blue, #3b82f6)`, and `var(--red, #ef4444)` permanently resolves to its hardcoded fallback, fully bypassing the theme system. Any future theme variant (light mode, high-contrast) cannot override these colours.

**Suggested fix:** Add three aliases to `css-generator.ts`:
```css
--orange: ${c.amber};      /* map to existing amber token */
--blue: ${c.accentDim};    /* or add a dedicated blue token */
--red: ${c.error};         /* map to existing error token */
```
Alternatively, normalise references in the seven components to use `--amber`, `--accent-dim`, and `--error` respectively.

### BUG-04 · MEDIUM · `rehype-sanitize` permits `style` attribute on `<span>` in rendered learn content

**File:** `src/lib/content/markdown.ts:25`

```typescript
span: [...(defaultSchema.attributes?.['span'] || []), 'aria-hidden', 'style'],
```

**Explanation:** The KaTeX schema extension allows arbitrary `style` on every `<span>`. Any content author (or a compromised content file) can inject CSS properties via markdown (e.g. `<span style="color:red;background:url(//evil.example)">`) that will pass sanitization. This is a CSS injection vector, not an XSS vector, but it can break layout and is harder to audit than markup-level attacks.

**Suggested fix:** Restrict the `style` allowlist to only properties KaTeX legitimately emits, or replace the `style` attribute permission with a strict `className`-based approach:
```typescript
span: [...(defaultSchema.attributes?.['span'] || []), 'aria-hidden'],
```
Then test that KaTeX output remains correct — KaTeX uses inline `style` for positioning, so a whitelist of specific properties may be necessary.

### BUG-06 · LOW · `file` input inside `<label>` has no accessible name — `ScreenshotCapture.svelte:155–157`

**File:** `src/lib/components/feedback/ScreenshotCapture.svelte:155–157`

```svelte
<label class="action-btn">
    <input type="file" accept="image/png,image/jpeg,image/webp" onchange={onFileChange} />
    <span>{$t('feedback.screenshot.upload')}</span>
</label>
```

**Explanation:** The `<span>` text provides the label visually via DOM order, but screen readers will read the label as the file input's accessible name only if the `<span>` appears *before* the `<input>` — or if `aria-label` is present. With `<input>` before `<span>`, most screen readers announce "Choose File" (the browser default) instead of the translation string.

**Suggested fix:** Swap the DOM order so `<span>` precedes `<input>`, or add `aria-label={$t('feedback.screenshot.upload')}` directly on the `<input>`:
```svelte
<label class="action-btn">
    <span>{$t('feedback.screenshot.upload')}</span>
    <input type="file" accept="image/png,image/jpeg,image/webp" onchange={onFileChange} />
</label>
```

**Title FR:** Préparateur d'états financiers

**Pedagogical objective:** Students routinely post correct journal entries but cannot close them into the SYSCOHADA statements (Bilan, Compte de Résultat, TAFIRE). **Minimum viable inputs/outputs:**
- Input: Trial balance (account code, label, debit total, credit total)
- Output: Draft Bilan (Assets / Liabilities), Compte de Résultat (Charges / Produits), subtotals at each OHADA class boundary, balancing check, highlighted errors

**Why it complements existing playgrounds:** The Journal Entry playground stops at the ledger/trial balance stage. This playground picks up exactly there and teaches the terminal step of the accounting cycle that most OHADA students lose marks on in exams.

### IDEA-02 · Inventory Valuation — CMUP vs. FIFO (Valorisation des stocks)

**Title EN:** Inventory Valuation — CMUP vs. FIFO  
**Title FR:** Valorisation des stocks — CMUP vs. FIFO

**Target learner:** Licence 2, Licence 3

**Pedagogical objective:** SYSCOHADA mandates Weighted Average Cost (CMUP — Coût Moyen Unitaire Pondéré) as the primary inventory method, but students confuse it with FIFO and struggle to compute CMUP after each purchase (periodic vs. continuous). This playground makes the arithmetic visible and shows how method choice affects cost of goods sold and ending inventory.

**Core interaction:** The learner enters a sequence of purchase and sale events (quantity, unit price, date). The playground simultaneously computes and columns FIFO and CMUP side-by-side with a step-by-step ledger view. Sliders let learners inflate a late purchase price to observe how CMUP absorbs the shock compared to FIFO. A toggle switches between periodic CMUP (end-of-period recompute) and continuous CMUP (recalculate after each purchase).

**Minimum viable inputs/outputs:**
- Input: Opening balance, sequence of purchase/sale rows (date, qty, unit cost)
- Output: Perpetual inventory card (CMUP and FIFO columns), ending inventory value, COGS figure, OHADA-style inventory account entry summary

**Why it complements existing playgrounds:** No current playground covers inventory. CMUP is a mandatory SYSCOHADA topic in both Licence 2 accounting curricula and the DSCG exam, and the FIFO/CMUP comparison is a perennial exam question.

### IDEA-03 · VAT Computation (Taxe sur la Valeur Ajoutée — TVA)

**Title EN:** VAT / Sales Tax Computation  
**Title FR:** Calcul de la TVA

**Target learner:** Licence 2, Licence 3, practicing professional

**Pedagogical objective:** VAT mechanics — deductible input tax, output tax collected, net position (due or refundable), and the OHADA journal entries to record it — are conceptually simple but procedurally error-prone. Students confuse tax-inclusive and tax-exclusive prices, and miss the timing of deductibility rules.

**Core interaction:** The learner enters a set of purchases (amount HT or TTC, tax rate, deductible %) and sales (amount HT or TTC, tax rate) for a period. The playground computes TVA collectée, TVA déductible, solde dû / crédit de TVA, and generates the two SYSCOHADA journal entries (TVA collectée → compte 4431, TVA déductible → compte 4452). A toggle switches between inclusive and exclusive input modes. A "rate card" dropdown pre-fills standard OHADA-zone rates (18% CEMAC, 18% UEMOA, etc.).

**Minimum viable inputs/outputs:**
- Input: Purchase lines (HT/TTC, rate, deductibility %), sale lines (HT/TTC, rate)
- Output: TVA dashboard (collectée, déductible, net), journal entry table, running monthly ledger

**Why it complements existing playgrounds:** None of the six native playgrounds touch indirect tax. TVA is present in every OHADA accounting exam at Licence level and in every practitioner's monthly workflow.

### IDEA-04 · Partnership Profit Distribution (Répartition des bénéfices — SARL/SA)

**Title EN:** Partnership & Company Profit Distribution  
**Title FR:** Répartition des bénéfices SARL / SA

**Target learner:** Licence 3, Master

**Pedagogical objective:** OHADA Uniform Act on Commercial Companies mandates specific reserves and profit-allocation sequences (statutory reserve 5% until 10% of capital; optional reserves; dividends; carried forward). Students memorise the sequence but cannot compute it for non-round numbers or partial-year scenarios.

**Core interaction:** The learner enters net profit, share capital, existing statutory reserve, prior retained earnings, and proposed dividends per share. The playground walks through the OHADA allocation waterfall step by step: statutory reserve → optional reserve → dividends → retained earnings carry-forward, highlighting each constraint (e.g. "reserve is now ≥ 10% of capital — mandatory contribution stops"). The output is the formal resolution table used in an Annual General Meeting and the corresponding SYSCOHADA journal entries (compte 120 → 111, 113, 457, etc.).

**Minimum viable inputs/outputs:**
- Input: Net income, share capital, existing statutory reserve, prior retained earnings, proposed dividend per share, share count, optional reserve amount
- Output: Allocation table (statutory + optional reserve, dividends, carry-forward), AGM resolution text, journal entry

**Why it complements existing playgrounds:** Profit distribution is a pure accounting-cycle topic (the final step after the financial statements are closed) that links directly to the Financial Statement Builder idea above. It is frequently tested at Master level and in professional exams (DESCOGEF).

### IDEA-05 · Effective Interest Rate & Loan Comparison (Taux Effectif Global — TEG)

**Title EN:** Effective Interest Rate & Loan Comparison (TEG/APR)  
**Title FR:** Taux Effectif Global et comparaison de crédit

**Target learner:** Licence 2, Licence 3, practicing professional

**Pedagogical objective:** The Amortization playground computes a single loan schedule. This playground focuses on the *comparison* decision: given two or more competing loan offers with different fees, insurance costs, and rate types (fixed, variable), compute the TEG (Taux Effectif Global — the OHADA/CEMAC regulatory APR disclosure) and rank offers by true cost. Students consistently mistake the nominal rate for the effective cost.

**Core interaction:** The learner enters 1–3 loan offers side by side (principal, nominal rate, term, origination fees, mandatory insurance, compounding frequency). The playground computes the TEG for each using the actuarial method (solving for the IRR of the fee-inclusive cash flows — reusing `src/lib/finance/irr.ts`), renders a cost-waterfall chart (interest vs. fees vs. insurance), and highlights which offer is cheapest on a TEG basis versus a total-cost basis (they can differ).

**Minimum viable inputs/outputs:**
- Input: Up to 3 loan offers — principal, rate, term (months), fees, insurance/month
- Output: TEG per offer, total cost breakdown, ranked comparison table, amortization schedule for winner

**Why it complements existing playgrounds:** The Amortization playground handles *one* loan; this handles the *selection* decision. It reuses `irr.ts` and the existing amortization engine and fills a practical professional gap (TEG disclosure is legally mandatory in CEMAC and UEMOA credit agreements).
