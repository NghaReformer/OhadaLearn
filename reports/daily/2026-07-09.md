### Medium

**#2 — Hardcoded hex colour map in `CategoryBreakdownDonut.svelte`**
`src/lib/playgrounds/bank-reconciliation/components/CategoryBreakdownDonut.svelte:31–39`
`CATEGORY_COLORS` is a plain JS object mapping each item category to a raw hex string
(`#6ea8fe`, `#22c55e`, `#ef4444`, etc.). These values never change with the theme,
break if the palette is updated in `tokens.ts`, and are invisible to the design-token system.
**Fix:** Read colours at runtime with `getComputedStyle(document.documentElement).getPropertyValue('--accent')` etc., or define data-attribute colour slots that map categories to existing token variables.

**#3 — Hardcoded hex colour map in `MatchingPairsOverlay.svelte`**
`src/lib/playgrounds/bank-reconciliation/components/MatchingPairsOverlay.svelte:31–34`
Same pattern: `MATCH_COLORS` maps match-type strings (`exact-amount-ref`, `fuzzy`, `manual`) to
raw hex strings. Used as SVG `stroke` colours, they bypass the theme entirely.
**Fix:** Use a CSS class per match-type and define colour via `var(--accent)`, `var(--amber)`,
`var(--green)` in the component's `<style>` block; read the computed colour only when drawing the SVG overlay.

**#4 — `color: #fff` hardcoded across three route files**
- `src/lib/playgrounds/journal-entry/components/EntryHistory.svelte:400` — `.btn-confirm`
- `src/routes/[lang]/chart-of-accounts/+page.svelte:423, 458` — `.framework-btn.active`, `.class-chip.active`
- `src/routes/[lang]/learn/+page.svelte:202` — `.group-cta`

`#fff` is not a theme token; `tokens.ts` has no `--white` or `--text-on-accent` entry.

**Fix:** Add `textOnAccent: '#eef0f6'` to `ThemeTokens.colors` in `tokens.ts`, expose it as
`--text-on-accent`, and replace every `color: #fff` that sits on an accent/error background.

**#9 — `import type` from `$lib/server/` in a client component**
`src/lib/components/feedback/FeedbackForm.svelte:7`
```ts
import type { FeedbackType, FeedbackSeverity } from '$lib/server/db/types';
```
TypeScript erases type-only imports at runtime, so this won't leak server code to the client
bundle. However, SvelteKit's static boundary checker flags any import (including `import type`)
from `$lib/server/` in a non-server file during strict validation, and it makes the component
depend on a path it logically shouldn't know about.
`FeedbackType` and `FeedbackSeverity` are simple string-literal unions with no secrets.
**Fix:** Move these two type aliases to a new `src/lib/contracts/feedback.ts` (or add them to
the existing `src/lib/contracts/playground.ts` if appropriate) and import from there.

### Idea A — Inventory Valuation (FIFO / WAM / LIFO)

**Title (EN):** Inventory Valuation Methods
**Title (FR):** Méthodes d'évaluation des stocks

**Target learner:** Licence 2 — Financial Accounting

**Pedagogical objective:**
Students routinely confuse the cost-flow assumption with the physical flow of goods and
underestimate how inventory method choice affects gross profit and tax. This playground makes
the numerical divergence between FIFO, Weighted-Average Method (WAM — the SYSCOHADA default),
and LIFO viscerally visible.

**Core interaction:**
The learner creates a sequence of purchase lots (date, quantity, unit cost) and sales events,
then switches between FIFO / WAM / LIFO via a tab. A perpetual-inventory table recomputes in
real time showing unit cost used for each sale, ending inventory value, and gross profit.
A comparison strip at the bottom shows the three methods side-by-side.

**Minimum viable inputs / outputs:**
- Inputs: up to 10 purchase lots + up to 5 sale events; method selector (FIFO / WAM / LIFO)
- Outputs: perpetual stock card per method, ending inventory value, COGS, gross profit delta

**Why it complements existing playgrounds:**
The Journal Entry playground teaches the form of accounting entries; this one teaches the
economic substance that drives inventory COGS entries — directly extending Licence 2 content
and filling the Account 3x (Stocks) gap in the current catalog.

### Idea B — Tax Provision Calculator (IS / IRPP)

**Title (EN):** Corporate Tax Calculator
**Title (FR):** Calculateur d'impôt sur les sociétés (IS)

**Target learner:** Licence 3 / Master 1 — Fiscal Accounting / Tax Law

**Pedagogical objective:**
OHADA-zone students struggle to reconcile accounting profit with taxable income because
they do not internalise which charges are fiscally deductible and which must be re-added.
This playground teaches the reintegration/deduction table that bridges book profit to taxable
profit under SYSCOHADA + OHADA fiscal rules.

**Core interaction:**
The learner enters a pre-tax accounting profit, then works through a checklist of common
adjustments (non-deductible penalties, excess entertainment expenses, tax-exempt dividends,
carryforward losses). A running "fiscal result" indicator updates live. The final step
applies the applicable IS rate (33 % default, editable for Cameroon / Ivory Coast / Senegal
etc.) to produce the tax provision journal entry.

**Minimum viable inputs / outputs:**
- Inputs: accounting profit; up to 8 adjustment items (type + amount); applicable IS rate
- Outputs: reintegration table, taxable income, IS liability, net profit after tax, journal entry

**Why it complements existing playgrounds:**
No existing playground touches the tax dimension of financial statements. This is a natural
sequel to the Journal Entry playground for Licence 3 / professional-track students.

### Idea C — Foreign Exchange Revaluation

**Title (EN):** Forex Revaluation & Translation
**Title (FR):** Réévaluation des postes en devises

**Target learner:** Master 1 / Practicing professional

**Pedagogical objective:**
OHADA companies transact in XAF, EUR, USD, and GBP. Students misapply the spot rate vs.
closing rate distinction and generate wrong unrealised gain/loss entries on balance-sheet date.
This playground drills the SYSCOHADA rules for monetary vs. non-monetary item translation.

**Core interaction:**
The learner adds foreign-currency balances (asset or liability, original amount, historical
rate). At period-end they enter the closing exchange rate. The playground splits items into
monetary (revalued at closing rate → unrealised gain/loss to P&L) and non-monetary (kept at
historical rate). A summary shows the impact on the trial balance and the required
adjustment journal entry under the SYSCOHADA accounts (Écarts de conversion).

**Minimum viable inputs / outputs:**
- Inputs: up to 6 balance items (account, FC amount, currency, historical rate, closing rate)
- Outputs: revaluation table, net FX gain/loss, adjusting journal entries (SYSCOHADA accounts 476/477)

**Why it complements existing playgrounds:**
The currency formatter (`src/lib/format/currency.ts`) already supports 16 currencies and the
shared format/i18n systems handle locale-aware number display — the engine logic is the main
new piece. No existing playground addresses multi-currency accounting.

### Idea D — Financial Statement Builder (Trial Balance → Bilan / Compte de Résultat)

**Title (EN):** Financial Statement Builder
**Title (FR):** Construction des états financiers

**Target learner:** Licence 2 / Licence 3 — Financial Accounting

**Pedagogical objective:**
Students know how to post journal entries but struggle to classify trial balance accounts
into the correct SYSCOHADA financial statement sections. The mapping from account class (1–8)
to Bilan or Compte de Résultat is non-trivial and heavily tested in exams.

**Core interaction:**
The playground presents a pre-populated trial balance (editable amounts). The learner drags
each account line into the correct Bilan (Actif/Passif) or Compte de Résultat (Charges/Produits)
section. Instant feedback highlights misclassifications. Once all rows are placed, a one-click
"Validate" reconciles totals and shows the resulting Résultat net, confirming that Bilan balances.

**Minimum viable inputs / outputs:**
- Inputs: 15–20 trial balance lines (account code, label, debit, credit); drag-drop placement
- Outputs: completed Bilan, Compte de Résultat, pass/fail per line, net income reconciliation

**Why it complements existing playgrounds:**
The existing Journal Entry playground covers individual entries; this playground closes the
loop to the final output of the accounting cycle. Uses the same SYSCOHADA chart-of-accounts
data already powering `src/routes/[lang]/chart-of-accounts/`.

### Idea E — Budget Variance Analysis

**Title (EN):** Budget Variance Analysis
**Title (FR):** Analyse des écarts budgétaires

**Target learner:** Licence 3 / Master 1 — Managerial Accounting

**Pedagogical objective:**
Students can compute a total variance but rarely decompose it into price and volume (or
rate and efficiency) components, which is the core skill tested in management-accounting exams.
This playground makes the two-way decomposition tactile.

**Core interaction:**
The learner enters a standard cost card (standard quantity per unit, standard price) and actual
results (actual units produced, actual quantity used, actual price paid). The playground
computes and displays the price variance, quantity/efficiency variance, and total variance on a
waterfall chart. A "What-if" mode lets the learner move a slider to see which variance dominates.

**Minimum viable inputs / outputs:**
- Inputs: standard qty, standard price, actual qty, actual price, actual output
- Outputs: price variance, efficiency variance, total variance, waterfall chart, favourable/adverse labels

**Why it complements existing playgrounds:**
CVP analyses cost behaviour at the product level; variance analysis extends that into
performance-measurement territory. The `GoalSeekPanel` and `WhatIfPanel` patterns from the
CVP playground provide ready-made UI primitives. No current playground covers standard costing.
