**M-1 · Hardcoded `#fff` hex colors (4 occurrences) — violates CLAUDE.md**

All four are text-on-colored-background situations where the theme lacks a matching token. The `tokens.ts` file defines `--accent`, `--error`, etc. but no `--text-on-accent` or `--text-on-error` token, so devs fell back to a literal hex value.

| # | File | Line | Context |
|---|------|------|---------|
| a | `src/routes/[lang]/learn/+page.svelte` | 202 | `.group-cta` — text on `var(--accent)` CTA button |
| b | `src/routes/[lang]/chart-of-accounts/+page.svelte` | 423 | `.framework-btn.active` — text on `var(--accent)` active pill |
| c | `src/routes/[lang]/chart-of-accounts/+page.svelte` | 458 | `.class-chip.active` — text on `var(--accent)` class filter chip |
| d | `src/lib/playgrounds/journal-entry/components/EntryHistory.svelte` | 400 | `.btn-confirm` — text on `var(--error)` destructive button |

**Suggested fix:** Add tokens `textOnAccent` and `textOnError` to `src/lib/theme/tokens.ts`, then replace all four `color: #fff` with `color: var(--text-on-accent)` (a and b and c) and `color: var(--text-on-error)` (d). White text on a dark accent/error colour is currently correct visually, but the token system is incomplete without them.

---

**M-2 · Missing `--text-on-accent` / `--text-on-error` design tokens**

`src/lib/theme/tokens.ts` has no tokens for text rendered on the accent or error background colours. This is the root cause of M-1 and will recur in any future component that needs a coloured button label. Without the token, the linter cannot catch future violations automatically.

**Suggested fix:** Define `textOnAccent: '#ffffff'` and `textOnError: '#ffffff'` in the `colors` section of `tokens.ts` so the CSS generator emits `--text-on-accent` and `--text-on-error`.

**L-2 · Three separate `$effect` blocks in `VarianceScale.svelte:54–60` for tweened values**

```svelte
$effect(() => { tiltTween.set(tiltTarget); });
$effect(() => { bankTween.set(adjustedBank); });
$effect(() => { booksTween.set(adjustedBooks); });
```

Each `$effect` registers a separate subscriber and teardown cycle. The three values are independent, but because they likely all change together when props update, three separate effect runs in one microtask queue flush is unnecessary overhead.

**Suggested fix:** Merge into a single `$effect` block:
```svelte
$effect(() => {
  tiltTween.set(tiltTarget);
  bankTween.set(adjustedBank);
  booksTween.set(adjustedBooks);
});
```
This reduces the subscription count and guarantees the three tweens start in the same frame.

**L-3 · `ScreenshotCapture.svelte:156` — file input uses implicit label association only**

```svelte
<label class="action-btn">
  <input type="file" accept="image/png,image/jpeg,image/webp" onchange={onFileChange} />
  <span>{$t('feedback.screenshot.upload')}</span>
</label>
```

Wrapping `<label>` provides an implicit association that most modern screen readers handle correctly. However, NVDA on Firefox and some mobile assistants announce this input as "unlabelled file chooser" because the label text comes after the input element in DOM order and is inside a `<span>` (not a text node). Per WCAG 1.3.1, an explicit `id`/`for` pairing or `aria-label` on the `<input>` is more reliable.

**Suggested fix:** Add `id="screenshot-upload"` to the input and `for="screenshot-upload"` to the label, or add `aria-label={$t('feedback.screenshot.upload')}` directly on the `<input>`.

**L-4 · `cvp/exercises.ts:162` — unsafe `as unknown as CVPExerciseParams` cast**

```ts
return solver(params as unknown as CVPExerciseParams);
```

Double-cast via `unknown` bypasses TypeScript's structural type check entirely. If `params` ever diverges from `CVPExerciseParams` the compiler will not warn, and the runtime error will surface inside the solver, not at the call site.

**Suggested fix:** Narrow the type properly with a type guard or narrow at the upstream source. If the cast is genuinely needed (e.g. discriminated union), add an inline comment explaining why, so reviewers don't silently remove it.

**L-5 · Inconsistent ARIA role pairing in `chart-of-accounts/+page.svelte`**

The class filter buttons at line 153 are wrapped in a `role="tablist"` container, but the framework switcher buttons at line 134 are wrapped in `role="radiogroup"` with `role="radio"` on each button. Both are exclusive-selection button groups doing conceptually identical things (filter the account list). Using different ARIA patterns for the same interaction pattern is confusing for AT users and inconsistent for developers.

**Suggested fix:** Standardise on one pattern. Given neither set changes page routing (they filter in-place), `role="radiogroup"` + `role="radio"` + `aria-checked` is the semantically correct choice for both.

### Playground A — Balance Sheet Builder / Constructeur de Bilan SYSCOHADA

**Title EN:** SYSCOHADA Balance Sheet Builder
**Title FR:** Constructeur de Bilan SYSCOHADA

**Target learner:** Licence 1 / Licence 2

**Pedagogical objective:** Students consistently confuse the SYSCOHADA 9-class plan with IFRS or French PCG presentation rules — especially Class 1 (long-term financing), Class 4 (third-party accounts split between current assets and current liabilities), and the permanent capital / actif immobilisé structure. This playground closes that gap by forcing students to classify real account balances before computing totals.

**Core interaction:** A shuffled list of 15–20 pre-populated account balances (drawn from `src/lib/shared/chart-of-accounts/` OHADA data). Students drag each account into the correct cell of a two-column Bilan (Actif / Passif), sub-divided into the standard SYSCOHADA sections (Actif immobilisé, Actif circulant, Trésorerie-Actif; Capitaux propres, Dettes financières, Passif circulant, Trésorerie-Passif). The bilan totals update live; a "Check" button reveals misclassifications highlighted in red.

**Minimum viable inputs / outputs:**
- Input: account number, balance (pre-filled from scenario data)
- Output: populated Bilan table, Actif total, Passif total, balance check (Actif = Passif), per-item correctness feedback

**Why it complements existing playgrounds:** Journal Entry teaches _how_ to record transactions; this playground teaches _where_ those accounts land in the final statement. It is the natural next step after journal entries and directly uses the existing `chart-of-accounts` shared module and `PlaygroundScenarios` system.

### Playground B — TVA / Déclaration de TVA OHADA

**Title EN:** VAT Return Calculator (OHADA)
**Title FR:** Calculateur de Déclaration TVA (OHADA)

**Target learner:** Licence 2 / Licence 3, practicing professional

**Pedagogical objective:** TVA (taxe sur la valeur ajoutée) is the most frequent accounting task for OHADA-zone businesses, yet many students cannot correctly compute TVA collectée, TVA déductible, and the net TVA à décaisser / crédit de TVA. The varying rates across UEMOA (18 %), CEMAC (19.25 %), and country-specific exemptions compound the confusion.

**Core interaction:** Student enters a list of purchase and sales transactions with amounts and a "taxable / exempt / rate" selector per line. The playground accumulates TVA collectée (sales VAT) and TVA déductible (purchase VAT), applies the prorata deductibility rule for mixed businesses, and produces the monthly declaration summary: TVA brute, TVA déductible, solde à payer / crédit reportable. A "Apply Tax Period" toggle lets students compare quarterly vs monthly regimes.

**Minimum viable inputs / outputs:**
- Inputs: transaction type (achat/vente), HT amount, VAT rate selector (0 %, 18 %, 19.25 %, custom), deductibility flag
- Outputs: TVA collectée subtotal, TVA déductible subtotal, net TVA payable or credit, formatted declaration table, journal entries for TVA settlement (Class 445x accounts)

**Why it complements existing playgrounds:** No current playground covers indirect taxation. TVA touches Classes 4 and 6/7 — the same accounts students encounter in Journal Entry and the Balance Sheet Builder — making it a natural third layer in the accounting workflow sequence.

### Playground C — Financial Ratios Analyser / Analyse par les Ratios

**Title EN:** Financial Ratios Analyser
**Title FR:** Analyseur de Ratios Financiers

**Target learner:** Licence 3 / Master

**Pedagogical objective:** Students can read a balance sheet but cannot interpret it. They memorise ratio formulas without understanding which signals matter for OHADA-zone credit decisions, supplier negotiations, or investor presentations. This playground trains pattern recognition: _given this ratio profile, what story is the business telling?_

**Core interaction:** Student starts from a pre-populated Bilan + Compte de Résultat pair (drawn from sector-specific OHADA scenarios: agribusiness, trading company, service firm). A dashboard of 12 ratios (liquidity, solvency, profitability, activity) updates instantly as the student edits any line item in the statements. A "What-if" slider lets students stress-test a single variable (e.g. reduce trade receivables by 20 %) and watch which ratios move and by how much.

**Minimum viable inputs / outputs:**
- Inputs: editable Bilan + Compte de Résultat cells, sector selector (agri / trade / service)
- Outputs: 12 computed ratios with colour-coded thresholds (industry benchmarks), narrative interpretation sentences (localised EN/FR), ratio trend chart when multiple periods are loaded

**Why it complements existing playgrounds:** CVP already covers profitability levers; this playground contextualises those levers in external financial analysis. It is the capstone connecting Journal Entry → Balance Sheet → Ratio Analysis in a single learning arc.

### Playground D — Overhead Allocation / Imputation des Charges Indirectes

**Title EN:** Overhead Cost Allocation
**Title FR:** Imputation des Charges Indirectes

**Target learner:** Licence 2 / Licence 3

**Pedagogical objective:** The existing CVP playground uses direct costing (contribution margin). SYSCOHADA exams also require full costing (coût complet) with overhead allocation — a concept students consistently confuse because allocation keys feel arbitrary. This playground makes the allocation key choice tangible: changing the key visibly changes the unit cost and reported profit.

**Core interaction:** Student defines 2–3 cost centres (e.g. Atelier A, Atelier B, Administration), enters direct costs and a pool of indirect charges, then chooses an allocation key (machine-hours, labour-hours, turnover %) per centre. The playground computes the full cost per unit for each product, the break-even at full cost (contrasted with the CVP break-even at direct cost), and a side-by-side comparison of profit under direct vs full costing.

**Minimum viable inputs / outputs:**
- Inputs: cost centre names, direct costs, indirect charge pool, allocation key type and quantities, units produced per product
- Outputs: cost statement table (charges directes + charges indirectes imputées = coût complet), per-unit full cost, full-cost break-even, direct-vs-full profit comparison

**Why it complements existing playgrounds:** CVP is a natural prerequisite. Together they cover the complete SYSCOHADA cost-accounting arc (direct → full → CVP analysis) and satisfy the Licence 2 _Comptabilité analytique_ module requirements.

### Playground E — Payroll Journal Entry / Journal de Paie

**Title EN:** Payroll Journal Entry
**Title FR:** Journal de Paie (Comptabilisation des Salaires)

**Target learner:** Licence 3, practicing professional

**Pedagogical objective:** Payroll is universally required but rarely taught interactively. Students struggle with the multi-line journal entry that records gross salary, employee deductions (CNPS salarial, IRPP/IPP), employer contributions (CNPS patronal, FDFP), and net pay — especially because the OHADA-zone rates differ by country (Cameroon, Ivory Coast, Senegal, Gabon each have distinct CNPS/IPRES rates and tax brackets).

**Core interaction:** Student inputs gross salary and selects the country (Cameroon, Ivory Coast, Senegal, or generic). The playground shows a step-by-step payroll slip (Bulletin de Paie) with each deduction computed, then builds the corresponding multi-line journal entry automatically (Classes 6, 4, 5 accounts). The student must verify the journal entry by confirming debit/credit amounts before the playground marks the exercise complete.

**Minimum viable inputs / outputs:**
- Inputs: gross salary, country selector, number of employees (for aggregate mode)
- Outputs: interactive pay slip with labelled deductions, auto-generated journal entry template, verify-and-submit exercise mode, total employer cost (salary + patronal charges)

**Why it complements existing playgrounds:** Journal Entry teaches the mechanics; this playground teaches the domain knowledge that drives a specific, high-frequency entry type. It extends the Journal Entry playground's exercise system with a real-world use case that practicing professionals can use as a reference tool.
