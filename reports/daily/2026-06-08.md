### #001 — Server boundary violated in client component
**Severity:** critical  
**File:** `src/lib/components/feedback/FeedbackForm.svelte:7`

```ts
import type { FeedbackType, FeedbackSeverity } from '$lib/server/db/types';
```

A client-side Svelte component imports from `$lib/server/` — the SvelteKit server-only boundary. TypeScript erases type-only imports at runtime, so this doesn't currently crash, but it is a latent danger: if `$lib/server/db/types` ever re-exports anything with a runtime value, or if the path is renamed to co-locate real server logic, the bundler will include server code in the client bundle. It also violates the architectural contract stated in CLAUDE.md.

**Suggested fix:** Move `FeedbackType` and `FeedbackSeverity` out of `$lib/server/db/types` into a shared types file such as `$lib/types/feedback.ts`, and import from there in both the server handler (`src/routes/api/feedback/+server.ts`) and this component.

### #002 — Hardcoded hex colors in chart overlay (bypasses theme)
**Severity:** high  
**File:** `src/lib/playgrounds/bank-reconciliation/components/MatchingPairsOverlay.svelte:31–34`

  'exact-amount-date': '#10b981',

  manual: '#6ea8fe',

Hard-coded hex strings used as SVG stroke colors for connection lines. These won't change when the theme changes and have no semantic relation to the token system.

### #004 — Hardcoded `#fff` on accent buttons (missing `--on-accent` token)
**Severity:** medium  
**File:** `src/routes/[lang]/learn/+page.svelte:202`

```css
.group-cta {
  background: var(--accent);
  color: #fff;   /* ← hardcoded */
}
```

The text colour for elements sitting on the accent background is hardcoded to white rather than referencing a token. If the accent colour is ever changed to a lighter hue (e.g., yellow or light-green for alternate themes), white text would fail WCAG AA contrast.

**Suggested fix:** Add `--on-accent` to the token system (defaulting to `#fff` for the current dark blue accent) and replace `#fff` with `var(--on-accent)` in every accent-background context.

### #006 — Hardcoded hex in SVG data-URI (select chevron icon)
**Severity:** medium  
**File:** `src/lib/components/feedback/FeedbackForm.svelte:322`

```css
.select {
  background-image: url("data:image/svg+xml,…stroke='%23555c74'…");
}
```

`%23555c74` is URL-encoded `#555c74`. This colour is baked into the SVG at CSS parse time and cannot respond to CSS custom property changes. If the `--text-muted` token is ever adjusted, the chevron stays the same tint.

**Suggested fix:** Replace the data-URI approach with an inline `<svg>` chevron rendered inside a wrapper element (positioned absolutely), or use a `mask-image` technique that lets you paint the icon via `background-color: var(--text-muted)`. Either approach keeps the icon colour in the token system.

### Idea A — Inventory Valuation (FIFO / CMUP)
**EN:** Inventory Valuation Methods | **FR:** Méthodes de valorisation des stocks

**Target learner:** Licence 2 (intermediate financial accounting)

**Pedagogical objective:** Students routinely confuse FIFO (Premier Entré, Premier Sorti — PEPS) with the Weighted Average Unit Cost (CMUP) method mandated by SYSCOHADA for most SME contexts. The key misconception is that CMUP changes on every receipt, not just at period-end. This playground makes that difference visceral.

**Core interaction:** A chronological list of stock movements (receipts with unit cost, issues with quantity). The learner can toggle between PEPS and CMUP-after-each-entry; both the running inventory card and the cost-of-goods-issued total update live. A split-view shows how the same set of transactions produces different gross margins.

**Minimum viable inputs / outputs:**
- Inputs: up to 10 rows of (date, movement type: receipt/issue, quantity, unit cost for receipts)
- Outputs: running stock value, cumulative COGS, closing stock value, gross margin comparison table

**Why it complements existing playgrounds:** Journal-entry already shows how to record stock movements; this playground shows _which amount_ to record — a prerequisite skill the journal-entry playground currently assumes.

### Idea B — VAT (TVA) Declaration Builder
**EN:** VAT Declaration Simulator | **FR:** Simulateur de déclaration de TVA

**Target learner:** Licence 3 / Master 1 (tax accounting, professional certification)

**Pedagogical objective:** Students confuse TVA collectée (output VAT on sales) with TVA déductible (input VAT on purchases) and struggle to compute TVA due vs. crédit de TVA. The OHADA zone has varied rates (18 % standard in Cameroon/Côte d'Ivoire, 19.25 % in Cameroun via special tax, zero-rated exports), adding to confusion.

**Core interaction:** The learner inputs a series of purchase and sale transactions, tagging each with the applicable VAT rate. The engine computes the monthly/quarterly VAT declaration: total output tax, total deductible input tax, tax payable or credit carried forward. A visual "tax funnel" shows the split.

**Minimum viable inputs / outputs:**
- Inputs: country selector (drives default rate), list of (purchase/sale, HT amount, VAT rate), period
- Outputs: TVA collectée total, TVA déductible total, solde net (payable or crédit), simplified declaration form preview

**Why it complements existing playgrounds:** Journal entry teaches the accounting entries (TVA collectée 4431, TVA déductible 4451); this playground teaches the fiscal logic that drives those entries, closing a curriculum gap between accounting and tax courses.

### Idea C — Payroll & Social Charges Calculator (Bulletin de Paie)
**EN:** Payroll Calculator | **FR:** Simulateur de bulletin de paie

**Target learner:** Licence 3 / Master (HR accounting, cost of labour)

**Pedagogical objective:** Payroll is a recurring pain point: students know the journal entry structure (Salaires bruts → charges patronales → net à payer) but cannot correctly compute CNPS employer/employee rates, IRPP brackets, or the difference between coût total employeur and salaire net. OHADA-zone specifics (Cameroun, Côte d'Ivoire, Sénégal variants) are rarely taught with concrete numbers.

**Core interaction:** The learner enters a gross salary and selects a country. The engine applies the correct CNPS/CRTV/IRPP rules and breaks down every line of the payslip. A cost-of-labour bar chart compares net take-home, employee deductions, and employer charges side-by-side.

**Minimum viable inputs / outputs:**
- Inputs: country (Cameroun / Côte d'Ivoire / Sénégal), gross monthly salary, dependents count (for IRPP allowances)
- Outputs: full payslip grid (gross, each deduction with rate × base, net), employer charges, total cost of labour, IRPP bracket workings

**Why it complements existing playgrounds:** Directly feeds back into journal entry (Class 6 vs. Class 4 accounts for payroll), and into CVP (labour as a variable vs. fixed cost in a breakeven scenario).

### Idea D — Foreign Currency Transaction & Exchange Differences
**EN:** Foreign Currency Accounting | **FR:** Comptabilisation des opérations en devises

**Target learner:** Master 1 / Master 2 (advanced financial accounting, SYSCOHADA Chapter 3 §35)

**Pedagogical objective:** SYSCOHADA requires re-translation of foreign-currency receivables/payables at the closing rate, with exchange differences (écarts de conversion) parked in Class 4 adjustment accounts — a rule that confuses students who expect P&L treatment (the IFRS approach). This playground makes the two-step process (initial recognition vs. year-end adjustment) concrete.

**Core interaction:** The learner records a USD/EUR invoice at the transaction rate, then adjusts at the closing rate. The playground shows the balance sheet impact (écart de conversion actif / passif) and contrasts it with what IFRS would book as an income statement line. A toggle lets students switch between SYSCOHADA and IFRS treatment to see the divergence.

**Minimum viable inputs / outputs:**
- Inputs: invoice currency, invoice amount (foreign), rate at invoice date, rate at year-end
- Outputs: initial entry in FCFA, year-end adjustment entry, balance sheet accounts affected (411/401 + 4787/4786), comparison table SYSCOHADA vs. IFRS

**Why it complements existing playgrounds:** Builds on interest (time-value framing of currency exposure) and journal entry (shows which accounts receive the adjustment), while covering OHADA-specific rules that no existing playground addresses.

### Idea E — Working Capital & Cash Conversion Cycle
**EN:** Working Capital Analyser | **FR:** Analyse du besoin en fonds de roulement (BFR)

**Target learner:** Licence 3 / Master (financial analysis, corporate finance)

**Pedagogical objective:** BFR (Besoin en Fonds de Roulement) is a core SYSCOHADA financial analysis ratio. Students learn the formula (BFR = stocks + créances clients − dettes fournisseurs) but cannot relate it to the operating cycle or explain why a negative BFR (e.g., large retail) is healthy. The cash conversion cycle (CCC) gives the dynamic view that static balance-sheet analysis misses.

**Core interaction:** The learner inputs sector-relevant balance sheet values (stock, trade receivables, trade payables) and income-statement sales. The engine computes DIO, DSO, DPO, and the resulting CCC, then benchmarks them against configurable industry norms. A timeline diagram animates the cash gap between paying suppliers and collecting from customers.

**Minimum viable inputs / outputs:**
- Inputs: annual sales (CAHT), average inventory, trade receivables, trade payables, COGS
- Outputs: DIO / DSO / DPO in days, BFR in FCFA, BFR as % of sales, CCC timeline diagram, qualitative interpretation (positive = requires financing, negative = self-financing)

**Why it complements existing playgrounds:** Sits downstream of amortization (CAPEX affects fixed assets, not BFR) and CVP (operating leverage context), and upstream of TVM (BFR changes require financing whose cost is a TVM problem). Fills a gap in financial analysis that the current playground set leaves entirely uncovered.
