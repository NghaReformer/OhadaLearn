#### C-1 · Server-type import in client component
**File:** `src/lib/components/feedback/FeedbackForm.svelte:7`
**Severity:** Critical
```ts
import type { FeedbackType, FeedbackSeverity } from '$lib/server/db/types';
```
`FeedbackForm.svelte` is a client-rendered Svelte component. Importing — even as `import type` — from `$lib/server/` violates the SvelteKit server-only boundary that CLAUDE.md mandates. While TypeScript erases `import type` at compile time, SvelteKit's Vite plugin performs static-path analysis and can reject this import, producing a build error in strict mode. More importantly, it breaks the architectural rule: client code must never reference `$lib/server/` paths.

**Fix:** Move `FeedbackType` and `FeedbackSeverity` to a shared (non-server) types file — e.g., `src/lib/contracts/feedback.ts` — and import from there in both the server module and the component.

#### M-4 · `requestFullscreen()` rejection leaves `isFullscreen` stale
**File:** `src/routes/[lang]/playgrounds/[slug]/+page.svelte:44–52`
**Severity:** Medium
```ts
function toggleFullscreen() {
    if (!document.fullscreenElement) {
        target.requestFullscreen(); // async — not awaited
        isFullscreen = true;        // set optimistically before resolution
    } else {
        document.exitFullscreen();
        isFullscreen = false;
    }
}
```
`requestFullscreen()` returns a `Promise` that can reject (browser permission denied, element not in DOM, etc.). When it does, the browser fires `fullscreenerror`, not `fullscreenchange`, so the existing `fullscreenchange` listener on line 57 does not reset `isFullscreen`. The UI then shows "Exit Fullscreen" when no fullscreen is active.

**Fix:** `await target.requestFullscreen()` inside an `async` function and catch the rejection to reset `isFullscreen = false`. Alternatively, derive `isFullscreen` solely from the `fullscreenchange` listener and remove the optimistic assignment.

### P-1 · Balance Sheet Completion Playground
**EN:** Balance Sheet Builder | **FR:** Constructeur de Bilan

**Target learner:** Licence 1 / Licence 2

**Pedagogical objective:** Students memorise account classifications without understanding why assets must equal liabilities + equity. This playground forces them to manipulate both sides of the equation and see the constraint in real time, building intuition for SYSCOHADA's Class 1–5 structure.

**Core interaction:** A split ledger shows a partial set of account balances. The learner drags each account to the correct bilan section (actif immobilisé, actif circulant, dettes financières, capitaux propres). A live running total shows Assets vs. Liabilities + Equity; the submit button unlocks only when the equation balances.

**Minimum viable inputs/outputs:**
- Input: 8–12 pre-seeded account balances (amounts configurable by scenario)
- Output: Validation of placement, algebraic balance check, colour-coded diff for wrong placements

**Complements existing playgrounds:** Journal Entry teaches *recording*; this teaches *reporting*. Together they cover the full cycle from transaction to financial statement.

### P-2 · Financial Ratios Interpreter
**EN:** Ratios Dashboard | **FR:** Tableau de Bord des Ratios

**Target learner:** Licence 3 / Master / Practicing professional

**Pedagogical objective:** Fix the misconception that ratio analysis is just plugging numbers into formulas. Learners must interpret whether a ratio signals financial health or distress in the OHADA context, where benchmarks differ from IFRS markets.

**Core interaction:** The learner enters a simplified income statement and balance sheet (or loads a scenario preset). The playground computes 8 ratios across liquidity, solvency, and profitability categories (e.g., Ratio de liquidité générale, Ratio d'endettement, Rentabilité des capitaux propres). Each ratio card shows the computed value, a SYSCOHADA-typical benchmark range, and a colour-coded health indicator. Hovering reveals the formula derivation.

**Minimum viable inputs/outputs:**
- Input: ~15 balance sheet line items + 5 P&L items
- Output: 8 ratio cards with value, benchmark band, traffic-light status, formula tooltip

**Complements existing playgrounds:** CVP and TVM deal with planning-phase numbers; Ratios deal with post-period performance analysis — a different decision-making context.

### P-3 · Inventory Valuation Comparator (FIFO vs CMUP)
**EN:** Inventory Valuation | **FR:** Valorisation des Stocks

**Target learner:** Licence 2 / Licence 3

**Pedagogical objective:** SYSCOHADA mandates the weighted-average cost method (CMUP) by default, but exam questions frequently ask students to compare it with FIFO. Most students cannot explain *why* the two methods produce different cost-of-goods-sold figures.

**Core interaction:** The learner enters a sequence of purchase lots (date, quantity, unit cost) and sale events (date, quantity). The playground renders a parallel table showing running inventory valuation under both FIFO and CMUP, with each movement's impact highlighted. A summary line shows ending stock value and COGS under each method, with the delta called out.

**Minimum viable inputs/outputs:**
- Input: Up to 10 purchase/sale rows with date, quantity, unit price
- Output: Two side-by-side running valuation tables; ending stock and COGS summary per method; delta panel

**Complements existing playgrounds:** Journal Entry shows *how* to record an inventory purchase; this shows *which value* to record and *why* it differs by method.

### P-4 · Cash Flow Statement Builder (Indirect Method)
**EN:** Cash Flow Statement | **FR:** Tableau des Flux de Trésorerie

**Target learner:** Licence 3 / Master

**Pedagogical objective:** Students can read a bilan and compte de résultat but cannot construct the cash flow statement from them. The indirect method reconciliation (starting from net income, adjusting for non-cash items and working capital changes) is consistently the hardest exam topic in SYSCOHADA financial reporting.

**Core interaction:** The learner is given a side-by-side view of N-1 and N balance sheets plus the income statement. They drag-and-classify each line-item change into Operating / Investing / Financing activities and mark adjustments as add-back or deduction. A running total shows the net change in cash. Final validation compares the computed cash change to the balance sheet's cash delta.

**Minimum viable inputs/outputs:**
- Input: Two balance sheet snapshots (N-1 and N) + income statement (~20 line items total)
- Output: Populated TAFIRE (SYSCOHADA's cash flow table) with correct/incorrect highlighting; net cash reconciliation

**Complements existing playgrounds:** This is the final leg of the financial statement cycle, closing the loop opened by Journal Entry and Balance Sheet Builder (P-1).

### P-5 · OHADA-Zone Payroll Calculator
**EN:** Payroll Calculator | **FR:** Calculateur de Paie

**Target learner:** Licence 3 / Master / Practicing professional

**Pedagogical objective:** Payroll accounting is required in every SYSCOHADA entity but is almost never taught interactively. Learners confuse gross salary, taxable base, CNPS contributions, and net-to-pay — and cannot produce the Class 6 journal entries automatically.

**Core interaction:** The learner inputs an employee's gross salary and selects an OHADA member state (Cameroon, Senegal, Côte d'Ivoire, etc.) to load that country's CNPS and income-tax (IRPP/IPTS) rate tables. The playground computes employer and employee contributions, taxable income under local rules, IRPP, and net salary. A one-click "Generate Journal Entry" button creates the debit/credit structure for accounts 661x/431x/447x ready for export.

**Minimum viable inputs/outputs:**
- Input: Gross salary, member state selector, optional allowances (transport, housing)
- Output: Payslip breakdown (gross → deductions → net); journal entry draft; country-specific rate display

**Complements existing playgrounds:** Journal Entry teaches the mechanics of recording; this provides the *payroll-specific numbers* that accountants actually need to record, bridging calculation and recording in one workflow.
