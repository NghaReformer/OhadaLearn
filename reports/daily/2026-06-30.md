### Issue 1 — Undefined CSS tokens `--orange`, `--blue`, `--red` always resolve to hardcoded hex

**Severity:** HIGH  
**Files:** 10 components (see list)

`tokens.ts` and `css-generator.ts` define no `--orange`, `--blue`, or `--red` custom properties. Every `var(--orange, #f59e0b)`, `var(--blue, #3b82f6)`, and `var(--red, #ef4444)` call silently falls through to the hardcoded hex fallback on every render. These colours are invisible to the theme system and will never reflect a theme change.

Affected files and approximate line ranges:

| File | Properties used |
|---|---|
| `src/lib/components/playground/KpiStrip.svelte:76` | `--orange` |
| `src/lib/playgrounds/amortization/components/ChartPanel.svelte:436–533` | `--orange`, `--blue`, `--green` (existing token — fine), `--red` |
| `src/lib/playgrounds/amortization/components/ScheduleTable.svelte:240–265` | `--orange`, `--blue`, `--red`, `--green` |
| `src/lib/playgrounds/amortization/components/InputsPanel.svelte:604–605` | `--red` |
| `src/lib/playgrounds/bank-reconciliation/components/LedgerPanel.svelte:149–209` | `--orange`, `--error` (defined — fine) |
| `src/lib/playgrounds/bank-reconciliation/components/BankStatementPanel.svelte` | `--orange` |
| `src/lib/playgrounds/bank-reconciliation/components/ReconciliationFlow.svelte` | `--orange`, `--blue` |
| `src/lib/playgrounds/bank-reconciliation/components/ScenarioWalkthrough.svelte` | `--orange` |

| `src/lib/playgrounds/bank-reconciliation/components/VarianceScale.svelte` | `--orange` |

**Suggested fix:** Add `--orange`, `--blue`, and `--red` as named semantic aliases to `tokens.ts` / `css-generator.ts`. Map them to semantically equivalent existing tokens or new dedicated values:
- `--orange` → alias of `--amber` (`#f5a623` already defined)
- `--blue` → alias of `--accent-dim` (`#6366f1`) or a new `indigo` token
- `--red` → alias of `--error` (`#f06070` already defined)

This is a one-file fix in `css-generator.ts` that eliminates all hex fallback exposure.

### Issue 2 — Client component imports types from `$lib/server`

**Severity:** MEDIUM  
**File:** `src/lib/components/feedback/FeedbackForm.svelte:7`

```ts
import type { FeedbackType, FeedbackSeverity } from '$lib/server/db/types';
```

SvelteKit's vite plugin blocks all imports from `$lib/server` in client-renderable files at the module level, including type-only imports (the check runs before TypeScript erasure in some configurations). This has not caused a build failure yet but is a latent risk and violates the boundary rule in CLAUDE.md.

**Suggested fix:** Extract `FeedbackType` and `FeedbackSeverity` to a shared non-server file, e.g. `src/lib/types/feedback.ts`, and import from there in both `FeedbackForm.svelte` and `src/lib/server/db/types.ts`.

### Issue 6 — Three consecutive `$effect` calls for related tweens in VarianceScale

**Severity:** LOW  
**File:** `src/lib/playgrounds/bank-reconciliation/components/VarianceScale.svelte:54–60`

```svelte
$effect(() => { tiltTween.set(tiltTarget); });
$effect(() => { bankTween.set(adjustedBank); });
$effect(() => { booksTween.set(adjustedBooks); });
```

Three separate effects subscribe to three independent reactive values, creating three separate subscriptions and three separate microtask flushes per render cycle. Svelte 5's scheduler will batch these if they run in the same flush, but splitting them unnecessarily increases subscriber count.

**Suggested fix:** Merge into a single `$effect`:
```svelte
$effect(() => {
  tiltTween.set(tiltTarget);
  bankTween.set(adjustedBank);
  booksTween.set(adjustedBooks);
});
```

### Idea A — TVA / VAT Compliance Calculator

**Title (EN):** VAT Compliance Simulator  
**Title (FR):** Simulateur de Conformité TVA  
**Target learner:** Licence 2–3, practicing professional  
**Pedagogical objective:** Students confuse TVA collectée (output VAT) with TVA déductible (input VAT) and miscalculate the net amount owed to the tax authority. OHADA-zone countries each have specific rates (18% Cameroun, Côte d'Ivoire; 19.25% Sénégal; 20% Maroc) and exemption categories. No existing playground covers fiscal compliance.

**Core interaction:** Learner inputs a series of purchase and sale transactions, selects the applicable OHADA-country rate, and classifies each line as taxable or exempt. The playground computes TVA collectée, TVA déductible, and TVA à décaisser / TVA à rembourser in real time, then generates the corresponding journal entries (accounts 4431, 4452, 4454).

**Minimum viable inputs / outputs:**
- Inputs: Transaction type (purchase / sale), HT amount, tax rate selector, exempt toggle
- Outputs: TVA collectée total, TVA déductible total, balance due / credit, journal entry preview

**Why it complements existing playgrounds:** Journal Entry shows how to record VAT entries once the amounts are known; this playground teaches learners how to calculate those amounts first. Natural prerequisite chain: TVA Simulator → Journal Entry Playground.

### Idea B — Inventory Valuation Methods (FIFO vs CMP)

**Title (EN):** Inventory Costing Playground  
**Title (FR):** Méthodes de Valorisation des Stocks  
**Target learner:** Licence 2, Licence 3  
**Pedagogical objective:** SYSCOHADA mandates the Coût Moyen Pondéré (CMP) method, yet students are also examined on FIFO for international comparisons. The main misconception is that all methods yield the same cost of goods sold — learners are surprised by how much profit differs under each method.

**Core interaction:** Learner builds a sequence of stock movements (entry with unit cost, exit with quantity). The playground maintains a running stock card for both methods simultaneously, highlighting divergence in carrying value and COGS after each movement. A toggle reveals the corresponding balance-sheet impact at period end.

**Minimum viable inputs / outputs:**
- Inputs: Movement type (entry/exit), quantity, unit cost (for entries)
- Outputs: Per-method running balance, unit cost, total COGS, ending inventory value, divergence delta

**Why it complements existing playgrounds:** Amortization covers non-current assets; this covers current assets. Bank Reconciliation surfaces inventory-related timing differences. Together they cover the full asset side of the SYSCOHADA balance sheet.

### Idea C — Payroll & Social Contributions (Zone OHADA)

**Title (EN):** Payroll Simulator — OHADA Zone  
**Title (FR):** Simulateur de Paie — Zone OHADA  
**Target learner:** Licence 3, Master, practicing professional  
**Pedagogical objective:** Payroll in OHADA-zone countries involves employer contributions (CNPS, CRTV taxe in Cameroun; CNSS in Sénégal) and employee deductions that students calculate incorrectly because the base, cap, and rates differ by country. The resulting journal entry (accounts 661, 431, 432, 447) is a common exam error.

**Core interaction:** Learner inputs gross salary, selects country (Cameroun, Côte d'Ivoire, Sénégal, Gabon), and the playground breaks down net pay step by step: taxable base, income tax (IRPP) brackets, employee social charges, employer charges. A second panel shows the payroll journal entry with all six account lines pre-filled.

**Minimum viable inputs / outputs:**
- Inputs: Gross salary, country selector, number of dependants (for IRPP)
- Outputs: IRPP table with marginal rates, employee deductions, employer charges, net pay, journal entry

**Why it complements existing playgrounds:** Journal Entry Playground has a payroll scenario but uses fixed numbers. This playground lets learners explore how country choice and salary level change every line — building intuition before they write the entry.

### Idea D — Financial Ratio Dashboard

**Title (EN):** Financial Ratio Analyser  
**Title (FR):** Tableau de Bord des Ratios Financiers  
**Target learner:** Licence 3, Master  
**Pedagogical objective:** Students can reproduce a balance sheet from journal entries (Journal Entry Playground output) but cannot interpret it. They memorise ratio formulas without understanding what a "dangerous" liquidity ratio looks like in practice or how changing one line affects multiple ratios simultaneously.

**Core interaction:** Learner inputs simplified B/S and P&L figures (or loads a preset SYSCOHADA scenario). The playground instantly computes 12 ratios across four families (liquidity, solvency, profitability, activity), colour-codes each against OHADA-sector benchmarks, and shows a spider/radar chart. Sliders let the learner adjust a single variable (e.g. increase trade payables) and watch all affected ratios shift in real time.

**Minimum viable inputs / outputs:**
- Inputs: 12–15 B/S and P&L line items; optional sector selector for benchmarks
- Outputs: Ratio cards (current ratio, quick ratio, D/E, ROE, ROA, asset turnover, etc.), radar chart, narrative colour-coded verdict

**Why it complements existing playgrounds:** The Journal Entry Playground already generates a balance sheet and income statement. Phase 2 could pipe that output directly into this ratio dashboard, creating a complete pedagogical arc from transaction → statements → analysis.

### Idea E — Budget Variance Analysis

**Title (EN):** Budget Variance Workshop  
**Title (FR):** Atelier d'Analyse des Écarts Budgétaires  
**Target learner:** Master, practicing professional  
**Pedagogical objective:** Management accounting students in OHADA institutions rarely get hands-on practice with variance analysis beyond textbook tables. The common confusion is between price variance and volume variance, and between favourable/unfavourable signs across revenue and cost lines.

**Core interaction:** Learner inputs a budget template (revenue by product, fixed costs, variable costs per unit) and then an actuals column. The playground decomposes each variance into price effect vs volume effect, flags favourable (F) / unfavourable (U) per SYSCOHADA convention, and suggests the most likely root cause from a menu of explanations the learner must confirm or reject.

**Minimum viable inputs / outputs:**
- Inputs: Budget and actual figures for up to 4 revenue lines and 6 cost lines
- Outputs: Variance table (amount, %, F/U flag), price-volume decomposition, flexible budget reconciliation, guided root-cause exercise

**Why it complements existing playgrounds:** CVP Playground shows the static break-even point; this playground extends that into dynamic budget control — what happens when actual sales volume diverges from plan. The two together cover the full managerial accounting arc taught in Licence 3 / Master programmes.
