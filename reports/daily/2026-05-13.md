## 1. Bugs & Issues

### 1.1 Emoji Icons Violate Design Constraint
**Severity: high**
`src/lib/data/playgrounds.ts:19,27,36,45,52,60,68`

CLAUDE.md mandates "No emoji icons." Every playground entry uses an emoji in the `icon` field (📐, 📊, 📒, 🏦, 📉, 🏧, 📈). These values propagate to `PlaygroundCard.svelte` and any nav that renders icons. The field type is `string` so replacing these with named icon identifiers (e.g. SVG symbol ids or Lucide icon names) would satisfy the constraint without breaking the interface.

**Suggested fix:** Replace emoji strings with named identifiers (`'chart-bar'`, `'book-open'`, etc.) and render via an `<Icon name={pg.icon} />` component backed by inline SVG sprites. Update `PlaygroundMeta.icon` type to a union of valid icon names.

### 1.2 Hardcoded Hex Color `#fff` Outside Theme Tokens
**Severity: medium**

| File | Line | Context |
|------|------|---------|
| `src/lib/playgrounds/journal-entry/components/EntryHistory.svelte` | 400 | `color: #fff;` |
| `src/routes/[lang]/learn/+page.svelte` | 202 | `color: #fff;` |
| `src/routes/[lang]/chart-of-accounts/+page.svelte` | 423, 458 | `color: #fff;` (×2) |

CLAUDE.md: "All colors/fonts/spacing via CSS custom properties from theme tokens — NEVER hardcode hex colors." The token system already exposes `--text-primary` (#eef0f6) and `--text-inverse` (white-equivalent) — one of these should be used instead.

**Suggested fix:** Replace every `color: #fff` with `color: var(--text-primary)` or add `--text-inverse: #ffffff` to `tokens.ts` and reference it.

### 1.3 Stale `staticFile` / `lineCount` Metadata for Migrated Playgrounds
**Severity: medium**
`src/lib/data/playgrounds.ts:26-38`

`cvp` (line 26) and `journal-entry` (line 35) both carry a `staticFile` path and a non-zero `lineCount`, yet both are fully registered as native Svelte modules (`registerPlayground('cvp', ...)`, `registerPlayground('journal-entry', ...)`). Because `isNativeModule = isRegistered(slug)` returns `true`, the `staticFile` is **never consumed at runtime** — the iframe branch is dead code for those two slugs.

Consequences:
- The orphaned HTML bundles (`cvp-playground.html`, `journal-entry-playground.html`, ~622 KB combined) are shipped in `static/` but never served.
- Future developers reading `playgrounds.ts` will incorrectly infer these are iframe playgrounds.
- `lineCount` is used nowhere at runtime but misleads migration tracking.

**Suggested fix:** Remove the `staticFile` and reset `lineCount: 0` for `cvp` and `journal-entry`. Delete the corresponding HTML files from `static/playgrounds/` (or move to an `_archive/` dir outside `static/`). Add a comment to `PlaygroundMeta` explaining that non-zero `lineCount` signals "not yet migrated."

### 1.4 `FeedbackForm` Submit Button Has No Accessible Loading Label
**Severity: low**
`src/lib/components/feedback/FeedbackForm.svelte:246`

```svelte
<button type="submit" class="primary-btn submit" disabled={formState === 'submitting'}>
```

When `formState === 'submitting'` the button is disabled but screen readers receive no announcement that submission is in progress. There is no `aria-busy` or live region update.

**Suggested fix:** Add `aria-busy={formState === 'submitting'}` to the button and an `aria-live="polite"` region that announces the result state (`'success'` / `'error'`) when it changes.

### 1.5 `context-toggle` Label Has No Visible Text for Screen Readers
**Severity: low**
`src/lib/components/feedback/FeedbackForm.svelte:208-210`

```svelte
<label class="context-toggle">
    <input type="checkbox" bind:checked={includeContext} />
```

The label element wraps the checkbox (implicit association — valid HTML), but the visible label text that follows is inside a sibling element. If the CSS hides or repositions content, the accessible name may be empty. Add `aria-label` or ensure the label text is a direct text child of `<label>`.

**Suggested fix:** Add `aria-label={$t('feedback.context.toggle')}` (add the key to both EN/FR namespaces) or restructure so the text node is a direct child of `<label>`.

### 1.6 `_registry.ts` `console.warn` Will Surface in Production
**Severity: low**
`src/lib/playgrounds/_registry.ts:14`

```ts
console.warn(`Playground "${slug}" is already registered. Overwriting.`);
```

This guard is useful in development but `console.warn` is visible in production browser consoles. A duplicate registration would indicate a module import order bug — better to `throw` in development builds and strip in production.

**Suggested fix:** Wrap with `if (import.meta.env.DEV) { throw new Error(...) }` so it becomes a build-time error during development and is eliminated in production bundles.

### 2.1 Financial Ratio Dashboard
**EN:** Financial Ratio Analysis | **FR:** Analyse des ratios financiers
**Target learner:** Licence 3 / Master 1
**Pedagogical objective:** Students memorize ratio formulas in isolation but struggle to interpret an interconnected set of ratios from a single balance sheet + income statement. This playground fixes the "formula without context" gap.
**Core interaction:** Learner inputs (or selects a scenario preset) key line items from a simplified SYSCOHADA bilan/résultat. The dashboard instantly computes and displays four ratio families — liquidité, solvabilité, rentabilité, activité — with colour-coded benchmarks and drill-down explanations.
**Minimum viable inputs:** Total assets, current assets, current liabilities, long-term debt, equity, revenue, net income, COGS, trade receivables, inventories.
**Outputs:** 8–10 named ratios, sparkline trend (3 periods), a plain-language interpretation per ratio.
**Why it complements existing playgrounds:** CVP covers internal cost decisions; this covers external financial health signalling — the logical next step after a student understands the income statement.

---

### 2.2 Cash Flow Statement Builder (Indirect Method)
**EN:** Cash Flow Statement (Indirect Method) | **FR:** Tableau de flux de trésorerie (méthode indirecte)
**Target learner:** Licence 3 / Master 1
**Pedagogical objective:** The indirect method reconciliation (net income → operating cash) is the most commonly failed DSCG/DECOFI exam question. Learners confuse the sign conventions for depreciation add-backs, working-capital changes, and non-cash items.
**Core interaction:** Learner is given a net income figure and a list of balance-sheet line-item changes. They drag each item into the correct section (Operating / Investing / Financing) and choose the sign (add / deduct). The engine checks the reconciliation and highlights errors in real time.
**Minimum viable inputs:** Net income, depreciation & amortisation, ΔAR, ΔInventory, ΔAP, CapEx, loan proceeds/repayments, dividends paid.
**Outputs:** Three-section cash flow statement, opening→closing cash reconciliation, score on sign and classification accuracy.
**Why it complements existing playgrounds:** Bank Reconciliation handles book↔bank cash; this handles cash-from-operations — a different but equally exam-critical reconciliation.

---

### 2.3 TVA / VAT Accounting Playground
**EN:** VAT Accounting | **FR:** Comptabilisation de la TVA
**Target learner:** Licence 2 / Licence 3
**Pedagogical objective:** In the OHADA zone, students consistently confuse TVA collectée (output VAT), TVA déductible (input VAT), TVA à décaisser, and the rules for non-deductible TVA on specific expense categories (vehicles, entertainment). This playground surfaces the full cycle.
**Core interaction:** Learner records a month's worth of purchase and sale invoices. The playground auto-populates the debit/credit entries for accounts 4431 (TVA collectée) and 4452 (TVA récupérable). At period end, learner declares the net TVA position and computes the payment or credit carry-forward.
**Minimum viable inputs:** List of sales invoices (HT + TVA rate), list of purchase invoices (HT + deductibility flag), opening TVA credit from prior period.
**Outputs:** T-accounts for 4431/4452, net TVA payable, journal entry for settlement, detection of common errors (mixing HT and TTC, wrong account codes).
**Why it complements existing playgrounds:** Journal Entry teaches mechanics; this applies those mechanics to the single most complex recurring transaction in any OHADA-zone SME's accounting cycle.

### 2.4 Profit Distribution Simulator (SA / SARL)
**EN:** Profit Distribution (Corporation) | **FR:** Répartition du résultat (SA / SARL)
**Target learner:** Licence 3 / Master 1
**Pedagogical objective:** SYSCOHADA has specific sequencing rules for profit appropriation: legal reserve (5 % until 10 % of share capital), statutory reserve, dividends, retained earnings. Students routinely apply the steps in the wrong order or miscalculate the distributable amount.
**Core interaction:** Learner is given a net income figure, accumulated losses, share capital, and current reserve balances. They work through each step in a guided wizard; the playground validates order and arithmetic at each step and generates the final journal entries (accounts 11x, 13x, 46x).
**Minimum viable inputs:** Net income, accumulated losses/retained earnings, share capital, legal reserve balance, statutory dividend percentage.
**Outputs:** Step-by-step appropriation table, journal entries for dividend declaration and reserve allocation, error flags for constraint violations (e.g. distributing before covering losses).
**Why it complements existing playgrounds:** Journal Entry covers individual transactions; this covers the annual close — the capstone transaction of the fiscal year.

### 2.5 Payroll Accounting (SYSCOHADA)
**EN:** Payroll Accounting | **FR:** Comptabilisation des salaires
**Target learner:** Licence 2 / Licence 3, practicing professional
**Pedagogical objective:** The payroll journal entry is misunderstood because it involves five simultaneous debit/credit movements: gross wage expense, employee social charges (retained), employer social charges, net pay payable, tax withheld. SYSCOHADA account codes (641, 421, 431, 447, 512) differ from French PCG — a common confusion for bilingual learners.
**Core interaction:** Learner inputs a gross salary and selects a country profile (Côte d'Ivoire, Cameroon, Sénégal — with pre-set contribution rates). The playground generates the full paie bulletin, decomposes the employer cost, and scaffolds the journal entry with blanks for the learner to fill in account codes and amounts.
**Minimum viable inputs:** Gross salary, country/contribution-rate profile, number of employees (for batch mode), month/year.
**Outputs:** Bulletin de paie breakdown, employer cost summary, complete journal entry (accounts 641, 421, 431, 447, 512), cross-check that debits = credits.
**Why it complements existing playgrounds:** No existing playground touches payroll. This fills the largest gap in the financial-accounting category and has direct relevance for practicing accountants in the OHADA zone.
