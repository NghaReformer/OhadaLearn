### MEDIUM — `NumberField` silently discards `min` and `max` HTML attributes

**Severity:** Medium  
**File:** `src/lib/components/playground/NumberField.svelte:52-61`

Props `min` (default `0`) and `max` (default `1e12`) are accepted and used for JS-side clamping in `handleInput`, but the underlying `<input>` element only receives `{step}` — `{min}` and `{max}` are never forwarded. Consequences: (1) browsers cannot show native out-of-range styling; (2) screen readers cannot announce the valid range to AT users; (3) HTML5 form validation constraints are absent.

**Fix:** Add `{min}` and `{max}` to the `<input>` element. Since `type="text"` ignores `min`/`max` natively, also add `aria-valuemin={min}` and `aria-valuemax={max}` and change type to `"number"` or use `role="spinbutton"` with those attributes.

### MEDIUM — Promise instantiated inside `$derived` in playground page

**Severity:** Medium  
**File:** `src/routes/[lang]/playgrounds/[slug]/+page.svelte:12-16`

```svelte
let nativeLoader = $derived(
    data.isNativeModule
        ? getPlayground(pg.slug).then((mod) => mod?.loadPlaygroundComponent())
        : null,
);
```

`$derived` is a pure-computation primitive; creating Promises inside it is an anti-pattern. Every time any reactive dependency recalculates the derived, a new Promise is created and the `{#await}` block resets (shows the spinner again). While `data.isNativeModule` and `pg.slug` don't change during the page lifecycle today, this pattern is fragile and will cause a visible flash if any upstream state ever updates.

**Fix:** Move the async load into a `$state` variable populated inside an `$effect` or `onMount`:
```svelte
let nativeLoader = $state<Promise<...> | null>(null);
onMount(() => {
    if (data.isNativeModule) {
        nativeLoader = getPlayground(pg.slug).then((mod) => mod?.loadPlaygroundComponent());
    }
});
```

### MEDIUM — `GoalSeekPanel.svelte` `$effect` re-seeds `targetProfitInput` incorrectly

**Severity:** Medium  
**File:** `src/lib/playgrounds/cvp/components/GoalSeekPanel.svelte:43-47`

```svelte
$effect(() => {
    if (targetProfitInput === '') {
        targetProfitInput = fmtNumber(targetProfit || 20000, 0, locale);
    }
});
```

The effect tracks `targetProfit` and `locale` reactively but only applies when `targetProfitInput === ''`. This is a mixed initialization + reaction pattern. If the parent changes `targetProfit` after the user has typed something, the input is silently stale. Also, the prop `targetProfit` is in the dependency set so this fires on every parent re-render where `targetProfit` changes, doing a string comparison on every cycle.

**Fix:** Initialize with a direct `$state(fmtNumber(targetProfit || 20000, 0, locale))` and expose a reset action if needed, rather than using an `$effect` to conditionally overwrite.

### Idea 1 — Trial Balance to Financial Statements
**EN:** Trial Balance → Financial Statements  
**FR:** Balance de vérification → États financiers

**Target learner:** Licence 2 / Licence 3

**Pedagogical objective:** Students can post journal entries but freeze when converting a trial balance into a compliant SYSCOHADA bilan (balance sheet) and compte de résultat (income statement). The leap from a flat debit/credit list to classified statements is where most Licence 2 students fail exam questions.

**Core interaction:** The learner is given a pre-populated trial balance with 15–20 OHADA-class accounts. They drag each account row into the correct section of the bilan or compte de résultat (or mark it as contra/closing). As they categorize, both statements build in real time. Totals auto-check and the learner sees whether assets = liabilities + equity.

**Minimum viable inputs/outputs:**  
- Input: editable trial balance table (account code, debit balance, credit balance)  
- Output: live SYSCOHADA-format bilan and compte de résultat; pass/fail per account placement; net income plug highlighted

**Why it complements existing playgrounds:** Journal Entry teaches how entries are posted; this playground teaches what those postings ultimately produce. It is the bridge between the journal-entry and tvm/amortization playgrounds. Leverages the existing `chart-of-accounts` classification logic (`src/lib/shared/chart-of-accounts/ohada-accounts.ts`) and the `AccountingStagePanel` pattern already prototyped in the journal-entry playground.

### Idea 2 — Cash Flow Statement Builder (Indirect Method)
**EN:** Cash Flow Statement — Indirect Method  
**FR:** Tableau des flux de trésorerie — Méthode indirecte

**Target learner:** Licence 3 / Master 1

**Pedagogical objective:** Learners consistently confuse profit with cash, and misclassify working-capital changes vs. investing activities. SYSCOHADA's TFT (Tableau des Flux de Trésorerie) has a specific indirect-method layout that differs from IFRS IAS 7 in its treatment of interest paid.

**Core interaction:** The learner inputs opening and closing balance sheet figures plus net income. The playground auto-suggests each balance-sheet movement as operating, investing, or financing — the learner confirms or reclassifies each line. The running cash total updates instantly. A final "why did cash change?" summary shows the reconciliation narrative.

**Minimum viable inputs/outputs:**  
- Input: net income, ±Δ for A/R, inventory, A/P, capex, long-term debt  
- Output: SYSCOHADA-formatted TFT with three sections; ending cash cross-checks to balance sheet cash position  
- Stretch: toggle between SYSCOHADA and IAS 7 to highlight differences

**Why it complements existing playgrounds:** Amortization teaches loan repayment cash flows; Journal Entry teaches accrual. This playground explicitly teaches the accrual-to-cash bridge — a concept no current playground addresses.

### Idea 3 — Foreign Currency Transaction Remeasurement
**EN:** Foreign Currency Transactions  
**FR:** Transactions en devises étrangères

**Target learner:** Licence 3 / Master / practicing professional

**Pedagogical objective:** OHADA-zone businesses transact heavily in EUR, USD, and XAF. Students misapply the historical rate vs. closing rate rule and forget to recognize exchange gains/losses (écarts de conversion) at period-end under SYSCOHADA Article 37.

**Core interaction:** The learner enters a foreign-currency receivable or payable (currency, amount, transaction date rate). They then advance a calendar slider to period-end and input the new exchange rate. The playground shows: initial recognition entry in XAF, remeasurement at period-end, unrealised gain/loss account, and balance sheet presentation. A side panel shows the SYSCOHADA-required note disclosure.

**Minimum viable inputs/outputs:**  
- Input: currency pair (EUR/XAF, USD/XAF), invoice amount, transaction rate, period-end rate  
- Output: two journal entries (initial + remeasurement), net XAF exposure, gain/loss magnitude  
- Reuses `fmtCurrency` and the 16-currency format system in `src/lib/format/currency.ts`

**Why it complements existing playgrounds:** No existing playground touches multi-currency. This fills a critical gap for students preparing for the CPA OHADA qualification where forex questions appear in 3 of 7 paper modules.

### Idea 4 — Partnership Profit Allocation
**EN:** Partnership Profit Allocation  
**FR:** Partage du résultat en société de personnes

**Target learner:** Licence 2 / practicing professional

**Pedagogical objective:** OHADA SNC/SARL learners struggle with the allocation waterfall: salary allowances to partners, interest on capital contributions, then residual split by ratio. Errors accumulate when any step produces a deficit.

**Core interaction:** The learner defines 2–4 partners, their capital balances, agreed salary allowances, and residual profit-sharing percentages. They enter the year's net income. The playground walks through each allocation tier in sequence, showing a running subtotal after each step. A dynamic table shows each partner's total credit and the resulting closing journal entry (debit Résultat, credit Compte Associé X).

**Minimum viable inputs/outputs:**  
- Input: partner names, capital amounts, salary allowances, interest rate on capital, residual ratios, net income  
- Output: allocation waterfall table, per-partner totals, journal entry preview  
- Edge case handling: net income insufficient to cover salary allowances (deficit allocation)

**Why it complements existing playgrounds:** Journal Entry covers transaction posting; this covers the year-end closing entry for partnerships — a distinct and frequently tested topic absent from the current catalogue.

### Idea 5 — VAT Calculation & Reporting (TVA)
**EN:** VAT Computation & Reporting  
**FR:** Calcul et déclaration de la TVA

**Target learner:** Licence 2 / practicing professional

**Pedagogical objective:** OHADA-zone TVA rules (typically 18–19.25% in West Africa) with partial deduction and the distinction between TVA collectée and TVA déductible trip up most Licence 2 students and many practitioners. The monthly/quarterly declaration logic is rarely taught interactively.

**Core interaction:** The learner inputs a list of sales (HT amount, TVA-taxable yes/no) and purchases (HT amount, deductible yes/no, asset vs. expense). The playground computes TVA collectée, TVA déductible, and the net TVA position (due or credit). It generates the simplified declaration form and the journal entries for both collection and payment/credit carry-forward.

**Minimum viable inputs/outputs:**  
- Input: list of sales transactions, list of purchase transactions, applicable TVA rate (configurable 18–20%)  
- Output: declaration summary table, net TVA due/credit, month-end journal entries  
- Reuses `fmtCurrency` formatter and the `NumberField` input component; TVA rate connects to the `AccountingStandard` preference

**Why it complements existing playgrounds:** No current playground covers indirect taxes. TVA is the highest-frequency accounting task for any OHADA-zone SME bookkeeper and appears in every professional certification exam.
