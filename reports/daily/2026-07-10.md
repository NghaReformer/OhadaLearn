## 1. Bugs & Issues

### CRITICAL

#### C-1 · Unhandled async rejection + Promise leak in playground loader
**File:** `src/routes/[lang]/playgrounds/[slug]/+page.svelte:12–16, 101–116`  
**Severity:** Critical

`nativeLoader` is declared as a `$derived` that calls `getPlayground(slug).then(...)`. Two problems compound:

1. The `{#await nativeLoader}` block at line 103 has **no `{:catch}` clause**. If the dynamic import fails (network error, missing chunk, wrong slug in registry), the spinner disappears and the user sees a completely blank pane with no error message — a silent production failure.
2. Because `nativeLoader` is `$derived`, any reactive dependency change (e.g., locale update) re-evaluates the derived expression, firing a **new, abandoned Promise** on each run. Each firing kicks off a parallel module load that may never be used.

**Fix:** Promote `nativeLoader` to a `$state` initialized once in `onMount` (or use `untrack` inside the derived), and add `{:catch err}` with an error UI — e.g., an error card re-using the existing `--error` token.

### HIGH

#### H-1 · Theme tokens `--orange`, `--blue`, `--red` referenced but never defined
**Files:** `src/lib/components/playground/KpiStrip.svelte:76`, `src/lib/playgrounds/amortization/components/ChartPanel.svelte:436–533`, `src/lib/playgrounds/amortization/components/ScheduleTable.svelte:240–265`, `src/lib/playgrounds/amortization/components/InputsPanel.svelte:604–605`, `src/lib/playgrounds/bank-reconciliation/components/LedgerPanel.svelte:175`, `VarianceScale.svelte`, `TransactionJournal.svelte`, `BankStatementPanel.svelte`, `ScenarioWalkthrough.svelte`, `ReconciliationFlow.svelte` (25+ occurrences total)  
**Severity:** High

`css-generator.ts` outputs only `--amber`, `--green`, `--error`. Variables `--orange`, `--blue`, and `--red` are not emitted by the theme system, so every `var(--orange, #f59e0b)`, `var(--blue, #3b82f6)`, and `var(--red, #ef4444)` **always falls through to the hardcoded hex fallback**. These colors cannot be restyled via the token system and will not follow any future theme update.

**Fix:** Add `orange`, `blue`, and `red` entries to `ThemeTokens`, emit them in `css-generator.ts`, and remove the hex fallbacks from component stylesheets.

#### H-3 · Stale goal-seek input after scenario change
**File:** `src/lib/playgrounds/cvp/components/GoalSeekPanel.svelte:43–47`  
**Severity:** High

```js
$effect(() => {
    if (targetProfitInput === '') {
        targetProfitInput = fmtNumber(targetProfit || 20000, 0, locale);
    }
});
```

Once the user types anything, the guard `targetProfitInput === ''` prevents re-initialization. When the parent loads a different scenario (changing `targetProfit`), the effect re-runs but leaves the stale user input unchanged. The goal-seek solver then runs against a mismatched target/scenario combination and reports a wrong break-even figure.

**Fix:** Track `targetProfit` changes explicitly. Use `$effect(() => { targetProfitInput = fmtNumber(targetProfit ?? 20000, 0, locale); })` and rely on the `oninput` handler to keep `targetProfitInput` a local shadow — or maintain a separate "dirty" flag to detect user overrides.

#### M-1 · Hardcoded hex color maps in visualization components
**Files:**  
- `src/lib/playgrounds/bank-reconciliation/components/CategoryBreakdownDonut.svelte:30–40`  
- `src/lib/playgrounds/bank-reconciliation/components/MatchingPairsOverlay.svelte:30–35`  
**Severity:** Medium

Both components define JS `Record<string, string>` color maps with raw hex literals (`'#6ea8fe'`, `'#22c55e'`, `'#ef4444'` etc.). The donut chart feeds these directly into `style="background: {seg.color}"` (line 120). These are entirely outside the theme token pipeline — a theme change cannot reach them.

**Fix:** Define named CSS custom properties for data-series colors in `tokens.ts` (e.g., `dataSeries: ['#6ea8fe', '#22c55e', ...]`) and emit them via `css-generator.ts`. Reference `getComputedStyle(document.documentElement).getPropertyValue('--data-series-1')` in JS, or switch to CSS classes with `background: var(--data-series-1)`.

#### M-2 · Bare `color: #fff` in 4 component stylesheets
**Files:**  
- `src/lib/playgrounds/journal-entry/components/EntryHistory.svelte:400`  
- `src/routes/[lang]/chart-of-accounts/+page.svelte:423, 458`  
- `src/routes/[lang]/learn/+page.svelte:202`

All four use `color: #fff` on elements with `background: var(--accent)` or `background: var(--error)`. While `#fff` works against the current dark palette, it silently breaks for light themes.

#### M-3 · ARIA tab pattern incomplete
**Files:** `src/lib/components/playground/PlaygroundTabs.svelte:19–30`, `src/lib/playgrounds/tvm/components/SolverPanel.svelte:122–143`, `src/lib/playgrounds/tvm/components/AnnuityPanel.svelte:154–170`, `src/lib/playgrounds/tvm/Playground.svelte:130–157`  
**Severity:** Medium

All four `role="tablist"` implementations use `role="tab"` on buttons with `aria-selected`, but:
- Tab buttons have no `aria-controls` pointing to a panel ID.
- The associated content containers have no `role="tabpanel"`, `id`, or `aria-labelledby`.

Screen readers and keyboard-only users cannot programmatically navigate from a selected tab to its panel via the ARIA relationship. WCAG 4.1.2 (Name, Role, Value) is violated.

**Fix:** Give each tab button `aria-controls="panel-{key}"` and give each panel `role="tabpanel" id="panel-{key}" aria-labelledby="tab-{key}"`.

#### M-4 · Unkeyed `{#each}` on dynamic lists in Journal Entry playground
**Files:**  
- `src/lib/playgrounds/journal-entry/components/TAccountView.svelte:65, 74`  
- `src/lib/playgrounds/journal-entry/components/EntryHistory.svelte:114`  
- `src/lib/playgrounds/journal-entry/components/AccountingStagePanel.svelte:190, 401, 417, 433`  
**Severity:** Medium

These lists change reactively (user adds/removes lines, switches accounts). Without a `(key)` expression Svelte patches by index, which can misrecycle DOM nodes and produce incorrect text content when items are inserted or removed.

**Fix:** Add stable keys. For entry lines use `(i)` (index) as a minimum, or a stable `id` field if available.

### Idea 1 — Balance Sheet Classifier / Classeur du Bilan SYSCOHADA

**Title (EN):** Balance Sheet Classifier  
**Title (FR):** Classeur du Bilan SYSCOHADA  
**Target learner:** Licence 1 / Licence 2  
**Pedagogical objective:** Students can memorize account codes yet misclassify them on the face of the balance sheet — confusing "Actif Immobilisé" vs. "Actif Circulant" (e.g., client receivables due in 18 months), or failing to understand the SYSCOHADA Revised balance sheet structure (Assets = Net Brut − Amortissements/Provisions). This fixes that gap.  
**Core interaction:** A shuffled list of SYSCOHADA-coded accounts (drawn from the plan comptable) appears in a sidebar. The learner drags each account card into one of the labelled balance sheet sections (Actif Immobilisé / Actif Circulant / Trésorerie-Actif on the left; Capitaux Propres / Dettes Financières / Passif Circulant / Trésorerie-Passif on the right). Instant colour feedback on each drop; a summary score on completion.  
**Minimum viable inputs/outputs:** 10–15 pre-built account sets drawn from `src/lib/data/chart-of-accounts`; score panel showing correct/incorrect with plain-language explanations keyed through i18n.  
**Why it complements existing work:** Journal Entry already records transactions; this teaches where those entries end up on the financial statement — the next conceptual step. Leverages the existing `AccountPicker` component and chart-of-accounts data already in the codebase.

### Idea 2 — Inventory Valuation Methods / Valorisation des Stocks

**Title (EN):** Inventory Valuation  
**Title (FR):** Valorisation des Stocks  
**Target learner:** Licence 2 / Licence 3  
**Pedagogical objective:** Students know the formula for CMUP (Coût Moyen Unitaire Pondéré) in isolation but cannot reconcile why FIFO vs. CMUP produces different income statements and closing stock values — or why SYSCOHADA Revised prohibits LIFO. This makes the comparison visceral.  
**Core interaction:** Learner enters a series of goods receipts (date, quantity, unit cost) and issues (date, quantity). A toggle switches between FIFO, CMUP (after each movement), and CMUP (end-of-period). The inventory card and profit-on-sale row update live, with a side-by-side diff column highlighting differences. Journal entries for the selected method auto-generate.  
**Minimum viable inputs/outputs:** Receipt/issue table (up to 10 rows); method toggle; inventory valuation summary; journal entry preview; SYSCOHADA-standard compte 31x/60x codes.  
**Why it complements existing work:** Depreciation and Amortization already model asset write-down; this is the equivalent for current assets. The existing `NumberField` and format utilities need no changes.

### Idea 3 — VAT Mechanics / Mécanisme de la TVA (SYSCOHADA/CEMAC)

**Title (EN):** VAT Mechanics  
**Title (FR):** Mécanisme de la TVA  
**Target learner:** Licence 2 / Licence 3, practicing professional  
**Pedagogical objective:** The most common practical error for OHADA-zone practitioners is misapplying the TVA prorata coefficient for mixed-use entities (exonerated + taxable revenues), and confusing TVA collectée vs. TVA déductible in the journal. This makes the flow tangible before real declarations.  
**Core interaction:** Learner inputs sales lines (amount, taxable yes/no, TVA rate) and purchase lines (amount, category, TVA rate). The engine computes: TVA collectée, TVA déductible brute, prorata coefficient, TVA déductible nette, and net TVA payable/receivable. Journal entries are generated and grouped by compte (4441 / 4452 / 4455). A toggle lets learners set the prorata manually to explore sensitivity.  
**Minimum viable inputs/outputs:** Sales table, purchases table, prorata toggle; TVA summary panel; journal entry preview with compte SYSCOHADA codes.  
**Why it complements existing work:** Journal Entry shows how to record; this shows *what* to record for TVA and *why* the numbers come out that way. Unique topic not covered by any existing playground.

### Idea 4 — Financial Ratios Dashboard / Tableau de Bord des Ratios

**Title (EN):** Financial Ratios Dashboard  
**Title (FR):** Tableau de Bord des Ratios  
**Target learner:** Licence 3, Master, practicing professional  
**Pedagogical objective:** Students can compute individual ratios but cannot interpret them together or link them to the underlying balance sheet/income statement lines. This playground closes the diagnostic gap — the same misconception that causes examiners to report "calcul juste, analyse absente."  
**Core interaction:** Learner fills in a simplified balance sheet (5–6 aggregate lines) and income statement (4–5 aggregate lines) — or loads a pre-built OHADA-sector scenario. Six ratio cards auto-compute: current ratio (liquidité générale), debt ratio (endettement), ROE, ROA, gross margin, and operating leverage. Each card shows a gauge calibrated against OHADA-typical sector benchmarks, a plain-language interpretation, and which input line to change to improve it.  
**Minimum viable inputs/outputs:** Balance sheet + P&L input grid; 6 ratio gauges; interpretation text keys through i18n; 3–4 pre-built scenarios (retail, construction, manufacturing — OHADA-zone norms).  
**Why it complements existing work:** Synthesises all other playgrounds into a diagnostic tool. The `KpiStrip` component already handles ratio display; this playground extends that pattern with gauges and benchmarks.

### Idea 5 — Lease Accounting: SYSCOHADA vs IFRS 16 / Contrats de Location

**Title (EN):** Lease Accounting  
**Title (FR):** Contrats de Location — SYSCOHADA vs IFRS 16  
**Target learner:** Master 1/2, practicing professional  
**Pedagogical objective:** SYSCOHADA Revised introduced a finance/operating lease split mirroring IAS 17, while the growing IFRS 16 adoption in OHADA multinationals requires right-of-use asset accounting. The side-by-side comparison eliminates the most common professional error: expensing finance lease payments as rent.  
**Core interaction:** Learner enters lease terms (start date, term, monthly payment, implicit rate, asset fair value). Engine classifies the lease (finance vs. operating) and computes the present value of future lease payments using the existing `pmt.ts` / `irr.ts` finance library. Two journal entry sequences appear side-by-side: SYSCOHADA treatment and IFRS 16 treatment. A year-one income statement and balance sheet impact comparison shows the depreciation/interest split vs. the flat rental expense.  
**Minimum viable inputs/outputs:** 5–6 lease term inputs; classification verdict with rationale; year-by-year amortisation schedule (reusing the amortization engine); dual journal entry preview.  
**Why it complements existing work:** Reuses `engine.ts` from the amortization playground (same PMT/PV maths) and the `ScheduleTable` component. Adds practitioner-level complexity not covered elsewhere and directly serves the Master-level curriculum gap.
